# Auth v2.1 — Phase 5 (Common Identity Resolver Foundation) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build one common backend identity-resolution mechanism (`auth_identities` table + `resolve_identity()` service) that maps a verified authentication-provider identity to exactly one existing AthFuelPath parent or athlete, and migrate the existing email/OTP login path (`POST /api/auth/email/verify`) onto it — without implementing Google, Apple, or any new UI, and without changing OTP behavior, session token format, TTL, or Phase 3 restoration.

**Architecture:** One new additive table (`auth_identities`) stores `(provider, provider_subject) → (parent_id XOR athlete_id)` mappings, with `provider_subject` as the authoritative stable key (the normalized email itself, for the `email` provider) and `email`/`email_verified` as non-authoritative metadata. One new service module (`api/services/identity_resolver.py`) exposes `resolve_identity(...)`, implementing exact-match-first / verified-email-auto-link-only-when-unambiguous / fail-closed-on-conflict. `email_auth_verify` is rewired to call the resolver after OTP success instead of its own inline parent-then-athlete lookup; it keeps 100% of its existing side effects (last_login_at stamp, login-alert firing, response shape, session minting) — the resolver only answers "who owns this," the route still decides "what happens for that role."

**Tech Stack:** FastAPI + psycopg3 (Postgres). No new dependencies. One additive SQL migration (schema version 2 → 3).

**Spec:** User's Phase 5 kickoff message (this session) — the full detailed spec, referred to throughout as "the spec." Builds on `docs/superpowers/specs/2026-08-20-auth-onboarding-v2.1-design.md` and all four prior phase plans in this directory.

**Worktrees:**
- Backend: `~/FuelUpYouth-auth-v2.1`, branch `feature/auth-v2.1` (currently in sync with `main` at `6deac80` — clean).
- Mobile: **not required for this phase.** Investigation found no hard dependency forcing a mobile change (see Part A.6). If implementation surfaces one, it will be reported before being made, per the spec's explicit instruction.

**Explicitly out of scope for this phase** (per the spec — do not build any of this here): Google SDK/token verification/mobile button; Apple SDK/token verification/Sign-in-with-Apple button; OAuth redirects; Phase 6 social-login UI; Phase 7 public verified signup; Phase 8 invitation codes; refresh tokens; `jti`/session revocation; account-merging or account-linking UI; manual account-management UI; unrelated CORS/authorization/database cleanup; UI redesign.

## Part A — Investigation Results

### A.1 — Current parent/athlete identity resolution (the four known functions)

**`POST /api/auth/email/verify` — `email_auth_verify`, `api/routes/auth.py:66-146`**

Exact current order: OTP verify first (`verify_otp_code(email, code)`, 401 on failure) → `SELECT * FROM parents WHERE lower(email) = %s` (parent checked **first**, unconditionally) → if no parent, `SELECT * FROM athlete_logins WHERE lower(email) = %s` (athlete checked **second**) → if neither, return `{"verified": true, "has_account": false}` (no exception, no 404 — deliberate, since the caller already proved ownership of this email). Parent branch stamps `last_login_at` and backgrounds `login_alerts.notify_login` (Phase 4); athlete branch does neither. Both branches call `mint_session_token`. **There is no explicit disambiguation — "parent wins ties" is implicit in the fixed check order, not an explicit rule anywhere.** This is exactly the "separate parent-first/athlete-second identity system" the spec asks Phase 5 to replace with the common resolver.

**`mint_session_token` — `api/services/session_auth.py:54-73`**

`def mint_session_token(*, role: str, parent_id: Optional[int] = None, athlete_id: Optional[int] = None, ttl_seconds: int = TOKEN_TTL_SECONDS) -> str`. Payload is `{role, parent_id, athlete_id, exp}` only — no email, ever. Unchanged by this phase; the resolver hands its result to this function exactly as `email_auth_verify` does today.

**`GET /api/auth/session` — `get_session`, `api/routes/auth.py:149-194`**

Resolves purely from `identity.parent_id`/`identity.athlete_id` on the verified token payload — **no email involved anywhere in this path**. Confirmed untouched by anything in this phase; not a candidate for resolver migration (there's no external identity to resolve — the token already IS the resolved identity).

**`POST /api/auth/athlete-create-login/{athlete_id}` — `create_athlete_login`, `api/routes/auth.py:229-304`**

Phase 4's OTP gate: verifies `code` against `parent_email` directly via `verify_otp_code` (never through `/email/verify`), then rechecks parent-exists → athlete-belongs-to-parent → not-already-claimed, then inserts `athlete_logins` and mints an **athlete-only** session. Per the spec's explicit instruction ("should not accidentally create or relink a parent identity beyond what the common email identity model explicitly requires"), **this function is NOT migrated to the resolver in Phase 5.** Rationale: the OTP here is a one-time *authorization* proof ("this parent approves this claim"), not a *login* — routing it through `resolve_identity` would either (a) do nothing useful, since there's no existing identity to resolve for a login that's creating one, or (b) risk auto-linking/creating an `auth_identities` row for the parent as an unintended side effect of an athlete-claim action, which the spec explicitly warns against. Left untouched, as designed in Phase 4.

### A.2 — Two hidden email→identity resolution paths found (not previously known to any prior phase)

Beyond the four functions above, `api/routes/parents.py` contains a **second, independently-coded** parent-email-to-identity system that Phase 2/3/4 never touched:

- **`POST /api/parents/request-otp`** (`parents.py:56-78`) → `parents.py:61`: `SELECT id FROM parents WHERE lower(email) = lower(%s)`, **404s if no parent found** — this is enumerating by design (unlike `/api/auth/email/request`'s deliberately neutral response).
- **`POST /api/parents/verify-otp`** (`parents.py:81-99`) → `parents.py:86`: `SELECT * FROM parents WHERE lower(email) = lower(%s)`, a **second independent** email→parent resolution, then `verify_otp_code(...)`, returns `{"parent": ..., "athletes": ...}`. **Notably this route imports `mint_session_token` but never calls it — no `session_token` in its response at all**, despite looking like a login endpoint.
- **`GET /api/parents/exists?email=...`** (`parents.py:173-183`) → `parents.py:179`: `SELECT 1 FROM parents WHERE email = %s` — a standalone, unauthenticated, explicitly enumerating existence-check endpoint, sitting alongside the deliberately non-enumerating `/api/auth/email/request`.

**These are flagged, not fixed, in this plan.** They are not named anywhere in the spec's list of things Phase 5 must migrate (only `/api/auth/email/verify` is named), and touching them would be exactly the kind of "unrelated cleanup" the spec explicitly rules out. See Part I (Risks/Blockers) for the recommendation on what to do about them.

### A.3 — Everything else that touches `parents`/`athlete_logins` by email

Full sweep confirmed clean: `onboarding.py:35` and `parents.py:31` are post-INSERT read-backs on brand-new signup rows (not identity resolution of a caller-supplied email); `admin.py:454/459` matches a `feature_requests` row by an already-session-resolved parent's own email (not an auth path); `teamcoach_auth.py`/`teamcoach_admin.py` are a completely separate `coaches` table/auth system. ## Part B — Design

### B.1 — Proposed `auth_identities` schema

```sql
CREATE TABLE auth_identities (
    id               INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    provider         TEXT NOT NULL CHECK (provider IN ('email', 'google', 'apple')),
    provider_subject TEXT NOT NULL,
    parent_id        INTEGER REFERENCES parents(id) ON DELETE CASCADE,
    athlete_id       INTEGER REFERENCES athletes(id) ON DELETE CASCADE,
    email            TEXT,
    email_verified   BOOLEAN NOT NULL DEFAULT FALSE,
    created_at       TEXT DEFAULT sqlite_now(),
    updated_at       TEXT DEFAULT sqlite_now(),

    CONSTRAINT auth_identities_provider_subject_uniq UNIQUE (provider, provider_subject),
    CONSTRAINT auth_identities_exactly_one_owner CHECK (
        (parent_id IS NOT NULL AND athlete_id IS NULL) OR
        (parent_id IS NULL AND athlete_id IS NOT NULL)
    )
);
CREATE INDEX idx_auth_identities_parent_id ON auth_identities(parent_id);
CREATE INDEX idx_auth_identities_athlete_id ON auth_identities(athlete_id);
```

Design notes, matching this repo's existing conventions (confirmed against `001_baseline.sql`/`002_otp_codes_email.sql`):
- `id`: `INTEGER GENERATED BY DEFAULT AS IDENTITY` — same PK style as every other table in this schema, not `SERIAL`.
- `created_at`/`updated_at`: `TEXT DEFAULT sqlite_now()` — same string-timestamp convention as every other table (the custom `sqlite_now()` Postgres function exists specifically for this backward-compat reason, per Phase 1's investigation). `updated_at` is not strictly required by Phase 5's own logic (no row is ever updated post-creation in this phase — see B.3, "exact match is authoritative, never relinked"), but is included since the spec asks for "timestamps as appropriate" (plural) and it costs nothing to have available for Phase 6's eventual Google/Apple re-auth flows.
- `parent_id`/`athlete_id`: both nullable, both FK `ON DELETE CASCADE` (mirrors `athlete_logins.athlete_id`'s existing FK style) — deleting a parent or athlete cleans up their identity rows automatically, no orphans.
- **Ownership invariant enforced in the database**, per the spec's explicit ask ("Enforce this in the database if practical"): the `CHECK` constraint makes "exactly one of parent_id/athlete_id, never both, never neither" physically impossible to violate, not just an application-level convention.
- **Primary uniqueness rule enforced in the database**: `UNIQUE (provider, provider_subject)` — a duplicate insert attempt fails at the DB layer, not just in application logic.
- No `CHECK` constraint is added forcing `provider_subject`/`email` to already be normalized text (e.g. via a `lower(trim(...))` check) — normalization is enforced entirely at the application layer, in the resolver, for every row it ever writes (see B.3). This keeps the migration itself simple and matches the existing codebase's general pattern of app-layer-normalized-at-write-time rather than DB-layer-enforced-normalized (the same pattern `parents.email`/`athlete_logins.email` already follow, imperfectly, per A.5's finding).
- `provider` uses a `CHECK (provider IN (...))` rather than a Postgres native `ENUM` type — matches this schema's existing convention of plain `TEXT` columns with no native enum types anywhere in `001_baseline.sql`/`002_otp_codes_email.sql`.

### B.2 — Why `provider_subject = normalized email` for the `email` provider (evaluated, per the spec's explicit ask)

The spec says: "For the email provider, evaluate using the normalized verified email as the provider subject." This plan adopts that recommendation as final, for one concrete reason: there is no other stable, provider-issued subject identifier for email-based auth — unlike Google/Apple (which issue a permanent opaque `sub` independent of the user's current email address), "the email itself, proven via OTP" **is** the entire trust mechanism for this provider. Using the normalized email as `provider_subject` means `email` (the metadata column) and `provider_subject` (the key column) will always be identical for `provider = 'email'` rows — this redundancy is intentional and harmless: it keeps the table's shape uniform across all three providers (every row has a `provider_subject` that's the authoritative key, and an `email` that's informational metadata, even though for this one provider they happen to coincide), rather than special-casing the `email` provider's schema.

### B.3 — Common resolver contract

**New file: `api/services/identity_resolver.py`**

```python
from dataclasses import dataclass
from typing import Optional

from api.database import get_conn


@dataclass
class ResolvedIdentity:
    role: str  # "parent" | "athlete"
    parent_id: Optional[int]
    athlete_id: Optional[int]


class NoExistingAccount(Exception):
    """Verified identity, but no existing AthFuelPath owner matches. Signup
    (creating a new account) is Phase 7 — callers must not create one here."""


class AmbiguousIdentity(Exception):
    """The verified email matches more than one possible owner (e.g. the
    same normalized email exists as both a parent and an athlete login).
    Fail closed — never guess which owner is correct."""


def resolve_identity(
    *,
    provider: str,
    provider_subject: str,
    email: Optional[str] = None,
    email_verified: bool = False,
) -> ResolvedIdentity:
    """
    Resolve a verified authentication-provider identity to exactly one
    existing AthFuelPath parent or athlete.

    Resolution order:
      1. Exact (provider, provider_subject) match in auth_identities is
         authoritative — return it immediately, never relink based on a
         changed email.
      2. Otherwise, auto-link by email ONLY if email_verified is True and
         email is present, AND the normalized email matches EXACTLY ONE
         existing parent or athlete-login owner. On that single match,
         create the auth_identities row (so step 1 is authoritative next
         time) and return the resolved owner.
      3. No match at all -> raises NoExistingAccount (do not create one).
      4. More than one possible owner -> raises AmbiguousIdentity (fail
         closed; do not create anything, do not guess).

    provider/provider_subject/email are all expected pre-normalized by the
    caller (trim + lowercase for email-shaped values) — this function does
    not re-normalize, to keep the "what got compared" behavior fully
    visible/testable at the call site.
    """
    conn = get_conn()
    try:
        existing = conn.execute(
            "SELECT parent_id, athlete_id FROM auth_identities "
            "WHERE provider = %s AND provider_subject = %s",
            (provider, provider_subject),
        ).fetchone()
        if existing:
            row = dict(existing)
            return ResolvedIdentity(
                role="parent" if row["parent_id"] is not None else "athlete",
                parent_id=row["parent_id"], athlete_id=row["athlete_id"],
            )

        if not (email and email_verified):
            raise NoExistingAccount()

        parent = conn.execute(
            "SELECT id FROM parents WHERE lower(email) = %s", (email,)
        ).fetchone()
        athlete_login = conn.execute(
            "SELECT athlete_id FROM athlete_logins WHERE lower(email) = %s", (email,)
        ).fetchone()

        matches = []
        if parent:
            matches.append(("parent", dict(parent)["id"], None))
        if athlete_login:
            matches.append(("athlete", None, dict(athlete_login)["athlete_id"]))

        if len(matches) == 0:
            raise NoExistingAccount()
        if len(matches) > 1:
            raise AmbiguousIdentity()

        role, parent_id, athlete_id = matches[0]
        try:
            conn.execute(
                "INSERT INTO auth_identities "
                "(provider, provider_subject, parent_id, athlete_id, email, email_verified) "
                "VALUES (%s, %s, %s, %s, %s, %s)",
                (provider, provider_subject, parent_id, athlete_id, email, True),
            )
            conn.commit()
        except Exception as e:
            conn.rollback()
            if "unique" in str(e).lower():
                # Lost a race against a concurrent identical resolve — the
                # other request's insert already won; re-fetch its result
                # rather than erroring the caller for a benign race.
                existing = conn.execute(
                    "SELECT parent_id, athlete_id FROM auth_identities "
                    "WHERE provider = %s AND provider_subject = %s",
                    (provider, provider_subject),
                ).fetchone()
                if existing:
                    row = dict(existing)
                    return ResolvedIdentity(
                        role="parent" if row["parent_id"] is not None else "athlete",
                        parent_id=row["parent_id"], athlete_id=row["athlete_id"],
                    )
            raise

        return ResolvedIdentity(role=role, parent_id=parent_id, athlete_id=athlete_id)
    finally:
        conn.close()
```

This mirrors the existing codebase's established insert-uniqueness-handling idiom (`try/except` + `"unique" in str(e).lower()`, exactly as `create_athlete_login` already does — see `auth.py:288-299`) rather than introducing `ON CONFLICT DO NOTHING`, for house-style consistency.

**What this deliberately does NOT do**, per the spec: mint any session (`mint_session_token` stays the caller's job); create a new parent/athlete account when no owner is found (raises `NoExistingAccount`, Phase 7's job); apply any Gmail-specific normalization (no dot-stripping, no `+alias` stripping, no domain rewriting — the caller is responsible for exactly trim+lowercase, nothing more, matching the spec's explicit prohibition).

### B.4 — Migrating `email_auth_verify` to the resolver

Current inline logic (`auth.py:96-141`, parent-first-then-athlete) is replaced with a single `resolve_identity(provider="email", provider_subject=email, email=email, email_verified=True)` call (`email` is already normalized at this point — it's the same `email = data.email.strip().lower()` computed at `auth.py:87`, unchanged). The route then branches on the **result**, not on its own separate queries:

- `NoExistingAccount` → same as today's "neither matched" case: `return {"verified": True, "has_account": False}`.
- `AmbiguousIdentity` → **new case, currently unreachable in production** (A.5 confirmed zero email overlaps between `parents`/`athlete_logins` today) but must be handled defensively since it becomes structurally possible the moment any future write creates a collision. **Per 2026-08-24 mandatory clarification:** OTP verification already succeeded (this is genuine authentication proof), so this must NOT return 401 — 401 would incorrectly imply the caller failed to authenticate. Instead: log at `logger.error` server-side only (never sent to the client) and return `HTTPException(409, "Something went wrong. Please contact support.")`. The HTTP response body contains only that fixed generic string — no parent IDs, athlete IDs, emails, provider subjects, or any collision detail, in the response or in the server log line itself. No session is minted; the resolver has already guaranteed nothing was created.
- Success (`role == "parent"` or `"athlete"`) → the route does its **own** follow-up `SELECT * FROM parents WHERE id = %s` (or the athlete equivalent) to build the full response body — exactly the same pattern `get_session` already uses today (resolve identity → separately load the full row for the response). This is what preserves 100% of the existing side effects: the `last_login_at` stamp and `login_alerts.notify_login` background task still fire, unconditionally, only in the parent branch, exactly as today — they are not resolver concerns, they stay in the route handler.

Net effect: `email_auth_verify`'s response shapes, status codes, side effects (login alerts, `last_login_at`), and session-minting are **byte-identical** to today for every currently-reachable case. The only behavioral addition is the (currently unreachable) `AmbiguousIdentity` 409 path, and the fact that a successful resolve now also creates (or reuses) an `auth_identities` row as a side effect — invisible to the API contract, but permanent infrastructure for Phase 6.

### B.5 — Backfill migration strategy

Since A.5 confirmed **zero collisions on every dimension**, the backfill is fully deterministic — no ambiguous case exists anywhere in current production data, so no manual owner-choice or blocker applies. Two straight INSERT-SELECTs, explicitly normalizing at write time (per A.5's finding that ~78% of stored `parents.email` values and ~33% of `athlete_logins.email` values are not already normalized in storage):

```sql
INSERT INTO auth_identities (provider, provider_subject, parent_id, email, email_verified)
SELECT 'email', lower(trim(email)), id, lower(trim(email)), TRUE
FROM parents
ON CONFLICT (provider, provider_subject) DO NOTHING;

INSERT INTO auth_identities (provider, provider_subject, athlete_id, email, email_verified)
SELECT 'email', lower(trim(email)), athlete_id, lower(trim(email)), TRUE
FROM athlete_logins
ON CONFLICT (provider, provider_subject) DO NOTHING;
```

(`ON CONFLICT DO NOTHING` is used here, not the try/except pattern, because this is one-shot migration DML executed by the migration runner, not application request-handling code — matches `002_otp_codes_email.sql`'s own backfill style, which uses plain `UPDATE`/`INSERT` DML directly.) Given zero collisions, every `parents` row and every `athlete_logins` row gets exactly one corresponding `auth_identities` row; the `ON CONFLICT DO NOTHING` is a defensive no-op for this data, not a silent-collision-resolution mechanism.

**Mandatory execution-time fail-closed re-check (2026-08-24 review):** the planning-time preflight in A.5 is a point-in-time snapshot — production data can change before this migration actually runs. The migration file itself therefore repeats the same collision check at execution time, inside a `DO $$ ... RAISE EXCEPTION ... END $$` block that runs BEFORE `CREATE TABLE`/the backfill inserts, in the same transaction the migration runner already wraps each file in. If any collision is detected at that moment, the whole file aborts — no table is created, no row is backfilled, nothing is guessed. This is what makes "if collisions exist, stop and report them as a migration blocker instead of guessing" true operationally, not just true as of the planning-time snapshot.

**No accounts are deleted, merged, or rewritten** — the backfill only ever adds new `auth_identities` rows; `parents`/`athlete_logins` are read-only inputs to it.

```python
        DO $$

            dup_parent_count INTEGER;

            overlap_count INTEGER;
        BEGIN
            SELECT COUNT(*) INTO dup_parent_count FROM (
                SELECT lower(trim(email)) FROM parents GROUP BY 1 HAVING COUNT(*) > 1

                SELECT lower(trim(email)) FROM athlete_logins GROUP BY 1 HAVING COUNT(*) > 1

            SELECT COUNT(*) INTO overlap_count FROM parents p
                JOIN athlete_logins a ON lower(trim(p.email)) = lower(trim(a.email));

            END IF;
        END $$;
    """)
```

```sql
-- auth v2.1 Phase 5: common identity resolver foundation.
--
-- auth_identities maps a verified authentication-provider identity
-- (provider + provider_subject) to exactly one existing AthFuelPath parent
-- or athlete. provider_subject is the STABLE authoritative key; email is
-- non-authoritative metadata (for the "email" provider they happen to be
-- the same normalized string, since email itself IS the trust mechanism
-- for that provider -- see the Phase 5 plan, section B.2).
--
-- Additive only. Does not touch parents/athlete_logins. Safe to apply to
-- production before the application code that reads/writes this table
-- ships -- the table simply goes unused until then.
--
-- FAIL-CLOSED PREFLIGHT (2026-08-24 review, mandatory): a 2026-08-24
-- planning-time check found zero collisions, but production data can
-- change between planning and the moment this file actually runs. This
-- migration therefore re-checks for collisions at EXECUTION time and
-- aborts the entire file (CREATE TABLE included -- one transaction per
-- migration file, per db/postgres_migrate.py's run_migrations) rather
-- than guessing an owner or partially backfilling. If this RAISEs, the
-- migration runner rolls back and stops -- rerun only after resolving the
-- reported collision by hand.

DO $$
DECLARE
    dup_parent_count INTEGER;
    dup_athlete_login_count INTEGER;
    overlap_count INTEGER;
BEGIN
    SELECT COUNT(*) INTO dup_parent_count FROM (
        SELECT lower(trim(email)) FROM parents GROUP BY 1 HAVING COUNT(*) > 1
    ) t;
    SELECT COUNT(*) INTO dup_athlete_login_count FROM (
        SELECT lower(trim(email)) FROM athlete_logins GROUP BY 1 HAVING COUNT(*) > 1
    ) t;
    SELECT COUNT(*) INTO overlap_count FROM parents p
        JOIN athlete_logins a ON lower(trim(p.email)) = lower(trim(a.email));

    IF dup_parent_count > 0 OR dup_athlete_login_count > 0 OR overlap_count > 0 THEN
        RAISE EXCEPTION
            'auth_identities backfill aborted: % duplicate parent email group(s), % duplicate athlete_login email group(s), % parent/athlete email overlap(s) found at migration time. Resolve manually before rerunning -- do not guess an owner.',
            dup_parent_count, dup_athlete_login_count, overlap_count;
    END IF;
END $$;

CREATE TABLE auth_identities (
    id               INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    provider         TEXT NOT NULL CHECK (provider IN ('email', 'google', 'apple')),
    provider_subject TEXT NOT NULL,
    parent_id        INTEGER REFERENCES parents(id) ON DELETE CASCADE,
    athlete_id       INTEGER REFERENCES athletes(id) ON DELETE CASCADE,
    email            TEXT,
    email_verified   BOOLEAN NOT NULL DEFAULT FALSE,
    created_at       TEXT DEFAULT sqlite_now(),
    updated_at       TEXT DEFAULT sqlite_now(),

    CONSTRAINT auth_identities_provider_subject_uniq UNIQUE (provider, provider_subject),
    CONSTRAINT auth_identities_exactly_one_owner CHECK (
        (parent_id IS NOT NULL AND athlete_id IS NULL) OR
        (parent_id IS NULL AND athlete_id IS NOT NULL)
    )
);

CREATE INDEX idx_auth_identities_parent_id ON auth_identities(parent_id);
CREATE INDEX idx_auth_identities_athlete_id ON auth_identities(athlete_id);

-- Backfill: one 'email'-provider identity row per existing parent and per
-- existing athlete login, normalized at write time (existing parents.email/
-- athlete_logins.email are NOT reliably pre-normalized in storage -- see
-- Phase 5 plan section A.5). A 2026-08-24 production preflight confirmed
-- zero normalized-email collisions across parents, across athlete_logins,
-- and between the two -- this backfill is fully deterministic, no owner
-- was guessed, and it never deletes/merges/rewrites an existing account row.

INSERT INTO auth_identities (provider, provider_subject, parent_id, email, email_verified)
SELECT 'email', lower(trim(email)), id, lower(trim(email)), TRUE
FROM parents
ON CONFLICT (provider, provider_subject) DO NOTHING;

INSERT INTO auth_identities (provider, provider_subject, athlete_id, email, email_verified)
SELECT 'email', lower(trim(email)), athlete_id, lower(trim(email)), TRUE
FROM athlete_logins
ON CONFLICT (provider, provider_subject) DO NOTHING;
```

## Part G — Migration safety assessment

- **Additive only**: one new table, two new indexes, two backfill `INSERT`s. No `ALTER`/`DROP` on `parents`, `athletes`, or `athlete_logins`.
- **Legacy email fields preserved**: `parents.email` and `athlete_logins.email` are untouched, still the source of truth for the backfill and for every other part of the app that isn't `email_auth_verify`.
- **Google/Apple not required**: `provider` accepts `'google'`/`'apple'` values but no such rows are created until Phase 6; the `CHECK` constraint permits them without requiring them.
- **Existing sessions untouched**: `mint_session_token`/`verify_session_token`/TTL/payload shape are not modified by this migration or this phase's code changes.
- **Rollback-safe**: `DROP TABLE auth_identities` (if ever needed) cleanly removes it with zero impact on any other table — nothing references `auth_identities` via foreign key from the other direction, and reverting `email_auth_verify`'s code (a plain `git revert` of Task 3's commit) restores the pre-Phase-5 inline logic with no data loss, since `parents`/`athlete_logins` were never modified.
- **Schema version**: increments 2 → 3 via the existing `schema_migrations` mechanism, exactly as `002_otp_codes_email.sql` did for 1 → 2.
- **Production migration can be applied before new application code**: **yes**, explicitly confirmed in Part F — this is the required and only safe order.

## Part I — Risks / Blockers

1. **No collision blocker exists today** — A.5's planning-time preflight found zero collisions on every checked dimension, and the migration itself now re-checks at execution time (B.5) and aborts the entire transaction if that's no longer true when it actually runs. Nothing in this plan requires stopping for a human to pick a winner among ambiguous accounts — either the runtime check passes and the backfill is fully deterministic, or it raises and nothing is written.

2. **Two hidden legacy email→identity paths in `parents.py` are left un-migrated, by design** (A.2). After this phase, there will be **two independently-coded** ways to resolve a parent by email in production: the new resolver-backed `/api/auth/email/verify`, and the untouched legacy `/api/parents/request-otp` + `/api/parents/verify-otp` pair (which still does its own inline `SELECT * FROM parents WHERE lower(email)`, and still never mints a session despite importing `mint_session_token`). This plan does not migrate or retire them because the spec names only `/api/auth/email/verify` for migration, and touching them would be exactly the "unrelated cleanup" the spec rules out. **Recommendation: raise this explicitly for a scoping decision before or during Phase 6** — once Google/Apple identities exist, having a second, resolver-unaware parent-login path sitting in production is a real architectural inconsistency (not a Phase 5 defect, but worth resolving before it's forgotten). Also flagging `GET /api/parents/exists` as a live, unauthenticated email-enumeration oracle — pre-existing, unrelated to this phase, noted for the same future-scoping conversation, not touched here.

3. **Resolved by 2026-08-24 mandatory clarification**: `AmbiguousIdentity` → `/api/auth/email/verify` returns 409 with a fixed generic message, never 401 (since OTP verification already succeeded), and the response/log contain zero identifying details. Currently unreachable in production data (A.5), so this is defensive correctness, not an urgent live risk.

4. **Stored email normalization inconsistency** (A.5: 46/59 `parents.email`, 4/12 `athlete_logins.email` are not stored in already-normalized form) is a pre-existing condition, not introduced by this phase. The backfill migration explicitly normalizes at write time so `auth_identities` doesn't inherit it. Not a blocker; noted so a future reader doesn't mistake `provider_subject`'s clean normalization for evidence that `parents.email`/`athlete_logins.email` are equally clean (they are not).

5. **Race-safety of the auto-link path** (B.3): two concurrent first-time logins for the same not-yet-linked email could both pass the "exactly one owner" check before either inserts; the `try/except` + `"unique" in str(e).lower()` re-fetch handles this the same way `create_athlete_login` already handles its own analogous race (Phase 4, confirmed sound in that phase's code-quality review) — not a new risk pattern, an established one being reused.
