# Auth v2.1 — Phase 6 (Google + Apple Sign-In) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship Google Sign-In and Sign in with Apple as first-class login methods, both proving identity **server-side** (never trusting a client-supplied email as proof) and both resolving through the existing Phase 5 `resolve_identity()` common resolver into the existing AthFuelPath session mechanism — with no new accounts created (that's Phase 7), no parallel session system, and Apple's Hide My Email / first-authorization-only-data quirks handled explicitly rather than assumed away.

**Architecture:** Two new backend verification endpoints (`POST /api/auth/google/verify`, `POST /api/auth/apple/verify`) each perform full server-side cryptographic verification of the provider's token (signature, issuer, audience, expiry, nonce), extract the provider's stable subject + verified email, and hand that to the *unchanged* `resolve_identity()` — mirroring exactly how `email_auth_verify` already does this for the `email` provider. One additive migration adds two partial-unique indexes (closing the "multiple identities per owner per provider" gap found during investigation) and two nullable metadata columns to `auth_identities` (Apple first-authorization name capture, Apple refresh-token storage for the Phase 10 revocation dependency). A new small resolver-adjacent function, `link_identity_to_owner()`, handles the one case `resolve_identity()` structurally cannot: linking a *verified* Apple identity to an *existing* account when Apple's own email (a Hide My Email relay address) doesn't match anything — using the existing OTP mechanism as secondary proof, never a typed email alone. Mobile adds a `react-native-nitro-google-signin`-or-equivalent Google button and `expo-apple-authentication`'s native Apple button to `app/(auth)/login.tsx`, above the existing "Continue with Email" flow, with Apple omitted on Android per Apple's own platform constraints.

**Tech Stack:** FastAPI + psycopg3 (Postgres) backend, no new Python dependencies beyond Google's official `google-auth` library and a JWT/JWKS library for Apple (`PyJWT` + `cryptography`, or `python-jose` — final pick in Task 1). Expo SDK 54 / React Native 0.81 / Expo Router mobile, requiring a **new EAS development build** (neither Google nor Apple native SDKs run in Expo Go).

**Spec:** User's Phase 6 kickoff message (this session, the full detailed spec) — referred to throughout as "the spec." Builds on `docs/superpowers/specs/2026-08-20-auth-onboarding-v2.1-design.md` and all five prior phase plans in this directory, especially Phase 5's resolver (`docs/superpowers/plans/2026-08-24-auth-v2.1-phase-5.md`).

**Worktrees:**
- Backend: `~/FuelUpYouth-auth-v2.1`, branch `feature/auth-v2.1` (currently in sync with `main` at `a4d409c` — clean).
- Mobile: `~/FuelUpYouth_Mobile/fuelup-mobile-auth-v2.1` (or wherever the feature worktree currently points — confirm sync with mobile `main` at `780a5fb` before Task 5 begins).

**Explicitly out of scope for this phase** (per the spec — do not build any of this here): Phase 7 signup/account creation; public signup; Phase 8 athlete invitation codes; Phase 9 forced reauthentication; Phase 10 deletion/revocation behavior itself (only its storage *prerequisite*); refresh tokens for AthFuelPath's own sessions; AthFuelPath session `jti`/general revocation; password authentication; Settings → linked-accounts UI; general account-merging UI; unrelated CORS changes; Google Places key cleanup; TeamCoach/admin authentication refactors; unrelated database cleanup.

### A.2 — Backend identity foundation (Phase 5, unchanged by this investigation)

`api/services/identity_resolver.py`'s `resolve_identity(*, provider, provider_subject, email=None, email_verified=False)` is **already provider-agnostic** — it was explicitly designed in Phase 5 to support `provider="google"`/`"apple"` values (the `CHECK (provider IN ('email','google','apple'))` constraint on `auth_identities` already allows them; several Phase 5 tests already exercise `provider="google"` as a stand-in for "some future non-email provider"). Its resolution order (exact-match-first, verified-email-auto-link-only-if-unambiguous, fail-closed otherwise) requires **zero changes** to serve Google/Apple — Phase 6's job is purely to produce `(provider, provider_subject, email, email_verified)` correctly and securely from each provider's raw credential, then call the exact same function `email_auth_verify` already calls.

`mint_session_token`/`GET /api/auth/session`/`session_auth.py` are untouched by Phase 5 and must remain untouched by Phase 6 — the spec is explicit ("do not create a parallel session system").

### A.3 — `auth_identities` constraint gap (confirmed, migration required)

Read directly from `db/postgres/003_auth_identities.sql` (already live in production, schema version 3): the table has exactly two constraints — `UNIQUE (provider, provider_subject)` and a `CHECK` enforcing exactly one of `parent_id`/`athlete_id`. **There is no constraint preventing a single parent (or athlete) from accumulating multiple identity rows for the same provider** — e.g. nothing today would stop two different Google `sub` values both linking to parent #42, if that ever happened via a bug or an edge case in a future auto-link path. This is a real, confirmed gap (not hypothetical) matching the spec's Section 9 concern, and must be closed with an additive migration (Task 1) — `UNIQUE(provider, provider_subject)` alone does not imply "at most one identity per owner per provider."

Current production data (from Phase 5's rollout verification, `a4d409c`): 71 `auth_identities` rows, all `provider='email'`, one per existing parent/athlete by construction (the Phase 5 backfill's own uniqueness guarantee) — **zero possible violations of the new constraint exist today**, confirmed by construction, not just assumed.

### A.4 — Google implementation approach (researched against current, live documentation — see citations in the research agent's report, summarized here)

**Library decision — flagged for explicit review, not pre-decided by this plan.** Two viable options, no single official Expo/Google recommendation between them:
- `@react-native-google-signin/google-signin` (current v16.1.4) — larger install base, longer track record, but **Android Credential Manager support is a paid tier**; the free tier uses Google's deprecated legacy Android Sign-In SDK, which Google is actively sunsetting.
- `react-native-nitro-google-signin` (current v2.1.0) — free Credential Manager support (the modern, non-deprecated Android path), Nitro-Modules-based, purpose-built for exactly this "backend verifies the ID token" shape, but a newer/smaller project.

Both require a custom EAS development build (neither works in Expo Go) and ship Expo config plugins. **This plan recommends `react-native-nitro-google-signin`** on the grounds that building new production auth on a library whose free tier depends on an API Google is actively deprecating is the wrong default — but this is presented as a recommendation for explicit sign-off in Task 5, not a unilateral choice, given no official source picks a winner and there's a real cost/maturity tradeoff either way.

**Client ID architecture (this is the most common integration bug per the research — stated explicitly so it isn't repeated here):** three separate Google Cloud OAuth client IDs are needed — **iOS** (authorizes the native app binary + URL-scheme redirect), **Android** (tied to package name + SHA-1 signing cert), and **Web** (this is the one that matters for backend verification — configuring the mobile SDK with `serverClientID`/`webClientId` = the Web client ID makes the returned ID token's `aud` claim equal the Web client ID, regardless of whether the request came from iOS or Android). **The backend verifies `aud == <WEB_CLIENT_ID>`, always, on both platforms — never the iOS or Android client ID.**

**Server-side verification:** Google's own official guidance is to use their `google-auth` Python library's `id_token.verify_oauth2_token(token, requests.Request(), WEB_CLIENT_ID)`, which internally checks signature (against `https://www.googleapis.com/oauth2/v3/certs`, rotated daily), issuer (`accounts.google.com`), audience, and expiry. It does **not** check `nonce` — that's an explicit, separate, app-level responsibility.

**Nonce/replay protection:** generate a random nonce on-device per sign-in attempt, SHA-256-hash it before passing to the native SDK's `nonce` parameter, send `{id_token, raw_nonce}` to the backend, and after `verify_oauth2_token` succeeds, independently hash `raw_nonce` and compare against `idinfo['nonce']` — reject if absent or mismatched. This closes a real gap the baseline Google library call leaves open.

**Fields available post-verification:** `sub` (the durable identity key — never key on email alone), `email`, `email_verified`, `aud`, `iss`, `exp`; `name`/`picture`/`given_name`/`family_name` only if the `profile` scope was granted (not required for this phase).

**Configuration values needed from Google Cloud Console before implementation can be tested** (see the full checklist in Part J): an OAuth consent screen, and 3 OAuth 2.0 client IDs (iOS/Android/Web) under the `fuelup-500318` GCP project (the same project already hosting Cloud Run/Cloud SQL) or a dedicated one if preferred.

### A.5 — Apple implementation approach (researched against current, live documentation)

**`expo-apple-authentication`** is iOS-only (`platforms: ['ios', 'tvos', 'expo-go']` per its own source — "It does not yet support Android or web"). `signInAsync()` returns `{user, state, fullName, email, realUserStatus, identityToken, authorizationCode}`. Required config: `plugins: ["expo-apple-authentication"]` + `ios.usesAppleSignIn: true` in `app.json`; if EAS Build skips prebuild for iOS (needs verification per A.1's hybrid-native-state finding), the entitlement (`com.apple.developer.applesignin: ["Default"]`) must also be confirmed/added directly in the already-committed `ios/` project.

**App Store Review (Guideline 4.8) — confirmed, not assumed:** the exact current guideline text requires offering "another login service" meeting three privacy criteria whenever a third-party/social login (e.g. Google Sign-In) is offered — Sign in with Apple is the only option that satisfies all three by construction, and none of the guideline's five exemptions apply to a youth sports nutrition consumer app. **Offering Google Sign-In makes offering Apple Sign-In effectively mandatory for App Store approval, not optional.** Both must ship together, exactly as the spec already requires.

**Server-side verification:** Apple's JWKS endpoint is `GET https://appleid.apple.com/auth/keys` (select by `kid`). Required checks, verbatim from Apple's own docs: signature (ES256, against the JWKS), `nonce`, `iss == https://appleid.apple.com`, `aud == <your client_id>`, `exp`. **Audience rule:** for the native iOS app, `aud`/`client_id` = the app's **bundle ID** (`com.fuelupyouth.app`); if a future web/Android flow is ever added, that flow's `aud` would be a separate **Services ID**, not the bundle ID — Phase 6's `aud` check is bundle-ID-only, since Apple Sign-In ships iOS-only this phase (see A.5's Android finding below).

**First-authorization-only data — confirmed exact behavior, safety-critical:** Apple's docs state plainly that `email`/`fullName` are shared "the first time the user logs in... If the user then uses Sign in with Apple on another device, the API doesn't ask for the user's name or email again," and instruct implementers to "immediately store it locally" on receipt, since there is no API to re-fetch it later. **The backend must persist whatever Apple returns on the very first successful `signInAsync()` call before doing anything else with it** — there is no second chance.

**Revocation prerequisite (Phase 10 dependency, investigated per the spec's explicit ask):** `POST https://appleid.apple.com/auth/revoke` requires a stored refresh token (or access token) — Apple's docs: *"If you don't have either token for the user, you can generate tokens when validating an authorization code."* That means: at first sign-in, the backend must exchange `signInAsync()`'s `authorizationCode` via `POST https://appleid.apple.com/auth/token` (using a `client_secret` JWT signed with the account-level Sign in with Apple private key, Team ID, and Key ID) to obtain a refresh token, then **persist that refresh token now** — it is the only way Phase 10 will ever be able to revoke a user's authorization later; there is no "look up tokens after the fact" API. This is a real, concrete Phase 6 deliverable (capture + store the refresh token), even though the revoke call itself is explicitly Phase 10's job, not this phase's.

**Android — no native path exists.** Apple's own docs point web/other-platform implementers to "Sign in with Apple JS" (a Services-ID-based web OAuth flow), not a native SDK — there is no Apple-blessed native Android module. **This plan recommends omitting Apple Sign-In on Android** (very common, and Guideline 4.8 is an App-Store/iOS-only requirement with no Play Store equivalent) rather than building a separate web-based Services-ID flow, which would be new scope (a second, structurally different Apple integration) not requested by the spec. Flagged for explicit confirmation in Task 5.

### A.6 — Apple Hide My Email first-link design (evaluated against the existing architecture)

The spec's own sketched example — verify Apple → resolver finds no owner via the relay email → user picks "Link my existing account" → types their real AthFuelPath email → OTP sent/verified against that email → **then** the Apple `provider_subject` is linked → session issued — is evaluated here rather than blindly implemented, per the spec's explicit instruction.

**This plan adopts the sketched flow's shape, with one concrete architectural decision:** implement it as a **small new function alongside `resolve_identity()`**, not as a special mode inside it. `resolve_identity()`'s whole contract is "verified provider proof + optional verified provider email → resolve," and conflating a *secondary, different-channel* proof (an OTP sent to a typed email) into that function would blur what "verified" means at its one entry point. Instead:

```python
def link_identity_to_owner(*, provider: str, provider_subject: str, parent_id: int) -> ResolvedIdentity:
    """
    Creates a new (provider, provider_subject) -> parent_id mapping for an
    OWNER ALREADY PROVEN by the caller via a separate, already-completed
    verification step (Phase 6: an OTP sent to and verified against that
    parent's existing AthFuelPath email). This function does NOT verify
    anything itself -- it is only reachable after the caller has already
    established ownership through a real, independent proof, and it never
    accepts athlete_id (parents only -- an athlete has no email of their
    own to send a secondary-proof OTP to in this flow; an athlete's Apple
    identity would need to resolve through resolve_identity() alone, or
    remain unlinkable until Phase 7/8 revisit athlete-side social login).
    Fails on any pre-existing (provider, provider_subject) or
    (provider, parent_id) conflict, matching resolve_identity()'s same
    race-safety idiom.
    """
```

The new backend flow (`POST /api/auth/apple/verify` → `POST /api/auth/apple/link-existing`, see Part C.3):
1. `POST /api/auth/apple/verify` runs full Apple JWT verification (Task 2), then calls `resolve_identity(provider="apple", provider_subject=sub, email=apple_email, email_verified=apple_email_verified)`.
2. If that raises `NoExistingAccount` (the common case for Hide My Email on first use — the relay address matches nothing), the response is **not** a plain "no account" — it's a distinct `{"linked": false, "apple_verified": true}` signal telling the mobile app "your Apple identity is real, but we don't know whose account this is; offer the link-existing-account path" (mobile UX detail in Task 5). Crucially, the backend does **not** persist anything at this point — the verified Apple `sub` is NOT stored yet, exactly matching the spec's "at no point may typing an existing account email alone link an Apple identity" — nothing is linkable from client state alone.
3. Mobile prompts for the user's existing AthFuelPath email, calls the **already-existing, unchanged** `POST /api/auth/email/request` (neutral, non-enumerating — no new endpoint needed here).
4. Mobile collects the resulting 6-digit code, then calls a new `POST /api/auth/apple/link-existing` with `{apple_identity_token, email, code}`. This handler: **re-verifies the Apple identity token from scratch** (never trusts a prior verification result carried in client state — the token itself, or a fresh one, must be re-submitted and re-checked, since Apple identity tokens are short-lived and re-verification is cheap and closes any window for a stale/substituted token), calls the existing `verify_otp_code(email, code)` (the exact same function `email_auth_verify` uses — **zero duplication of OTP logic**), and only after **both** checks pass, resolves `email` to **exactly one** existing parent (reusing the same "must be exactly one owner, fail closed on 0 or 2+" logic `resolve_identity()` already has internally — factored into a small shared private helper rather than copy-pasted, see Task 2), then calls `link_identity_to_owner(provider="apple", provider_subject=sub, parent_id=that_parent_id)`, then mints a session exactly as `email_auth_verify` does for its parent branch.

This satisfies every explicit constraint the spec lists: the stable Apple `sub` (not the relay email) becomes authoritative after linkage (it's the literal key stored); typing an email alone can never link anything (OTP verification is mandatory and happens server-side against that exact email); the existing secure OTP mechanism is reused rather than reinvented; no new account is ever created (Gate 2's "exactly one existing owner" check fails closed exactly like `resolve_identity()`'s own auto-link path — 0 or 2+ matches never links, never creates).

**Athlete accounts are explicitly out of this linking flow** — an athlete has no email-based OTP channel of their own in this architecture (their login email, once claimed via Phase 4, could theoretically receive an OTP via the *existing* `/api/auth/email/request`/`verify` path, but doing so would return `role: "athlete"` from a flow this plan scopes as parent-only for the Hide-My-Email link case, since the spec's sketch and the "existing AthFuelPath email" framing both read as parent-account-shaped). If an athlete's Apple relay email doesn't resolve, Task 2's tests should confirm the `{"linked": false, "apple_verified": true}` no-account signal is still returned safely (no crash, no leak) — athlete-side Hide-My-Email linking is left unaddressed, flagged as a known scope boundary in Part L, not silently ignored.

### A.7 — Apple first-authorization persistence design ("smallest safe storage")

Two nullable additive columns on `auth_identities` (Task 1's migration), rather than a new side table — this data is 1:1 with an identity row, provider-specific, and small:
- `provider_metadata JSONB NULL` — populated **only** for `provider='apple'`, **only** on the very first successful verification for a given `(provider, provider_subject)` (i.e. exactly when the row is first created, since Apple only sends this data at that moment) — stores `{"full_name": {"given_name": ..., "family_name": ...}}` (whatever non-null fields Apple actually returned; omit null fields rather than storing explicit nulls). Never overwritten on subsequent logins (Apple won't send it again, so there's nothing to overwrite with — but the code must not attempt to overwrite an existing value with a later `None` either, since a later, second `signInAsync()` call correctly returns `fullName: null`, and blindly overwriting would destroy the one copy that exists).
- `apple_refresh_token TEXT NULL` — populated **only** for `provider='apple'`, from the one-time `authorizationCode` → `/auth/token` exchange performed immediately after first verification succeeds. Stored using the same protection level as every other sensitive column in this database (Cloud SQL disk encryption at rest — no other column in this schema, including `otp_codes.code_hash` or session-adjacent data, uses application-level encryption beyond that baseline) — flagged explicitly in Part L as a decision point: if stricter protection is wanted for this specific column (e.g. envelope encryption via a KMS key), that's a deliberate scope increase beyond "smallest safe storage" and should be an explicit sign-off, not assumed.

Both columns are additive, nullable, and `provider='email'`/`'google'` rows are entirely unaffected (always `NULL`).

### A.8 — Mobile/backend call-site and dependency check

No hard mobile dependency beyond what's already scoped (Task 5). `GET /api/auth/session` (Phase 3) is untouched — a Google/Apple-originated session is byte-identical in shape/TTL/format to an email-originated one, so restoration continues to work with zero changes. Confirmed via A.2.

## Part B — Server-side verification contracts

### B.1 — Google

```python
# api/services/google_auth.py (new)

@dataclass
class VerifiedGoogleIdentity:
    sub: str
    email: str | None
    email_verified: bool

class GoogleVerificationError(Exception):
    """Signature/issuer/audience/expiry/nonce check failed. Message is
    generic and safe to log; never includes the raw token."""

def verify_google_id_token(id_token_str: str, raw_nonce: str) -> VerifiedGoogleIdentity:
    """
    Verifies a Google ID token using google.oauth2.id_token.verify_oauth2_token
    against GOOGLE_WEB_CLIENT_ID (env-configured), then independently verifies
    the nonce (verify_oauth2_token does NOT check nonce -- this is an
    additional, mandatory step): sha256(raw_nonce).hexdigest() must equal the
    token's 'nonce' claim. Raises GoogleVerificationError on any failure
    (invalid signature, wrong issuer, wrong/unapproved audience, expired,
    missing/mismatched nonce). Returns sub/email/email_verified on success.
    """
```

`GOOGLE_WEB_CLIENT_ID` is a single configured value (not a secret — see Part J) read from environment/Secret Manager at startup, matching this codebase's existing pattern for `APP_SESSION_SECRET`.

### B.2 — Apple

```python
# api/services/apple_auth.py (new)

@dataclass
class VerifiedAppleIdentity:
    sub: str
    email: str | None
    email_verified: bool

class AppleVerificationError(Exception):
    """Signature/issuer/audience/expiry/nonce check failed."""

def verify_apple_identity_token(identity_token: str, raw_nonce: str) -> VerifiedAppleIdentity:
    """
    Fetches/caches Apple's JWKS (https://appleid.apple.com/auth/keys),
    selects the key matching the token's kid, verifies signature (ES256),
    iss == 'https://appleid.apple.com', aud == APPLE_BUNDLE_ID
    ('com.fuelupyouth.app'), exp, and nonce (Apple's SDK hashes the nonce
    the same way Google's does -- sha256(raw_nonce).hexdigest() compared
    against the token's nonce claim). Raises AppleVerificationError on any
    failure. Returns sub/email/email_verified.
    """

async def exchange_authorization_code_for_refresh_token(authorization_code: str) -> str:
    """
    One-time, first-authorization-only. POSTs to
    https://appleid.apple.com/auth/token with client_id=APPLE_BUNDLE_ID,
    client_secret=<freshly-signed ES256 JWT, see _build_apple_client_secret>,
    code=authorization_code, grant_type=authorization_code. Returns the
    refresh_token from the response. Raises AppleVerificationError (or a
    dedicated subclass) on failure -- this must NOT block session issuance
    if it fails (the user's login should still succeed even if the
    Phase-10-prerequisite refresh-token capture fails; log and continue,
    matching this codebase's existing "non-blocking side effect" pattern
    used for login_alerts.notify_login).
    """

def _build_apple_client_secret() -> str:
    """
    Builds the ES256-signed JWT client_secret Apple's token/revoke
    endpoints require: header {alg: ES256, kid: APPLE_KEY_ID}, payload
    {iss: APPLE_TEAM_ID, sub: APPLE_BUNDLE_ID, aud: 'https://appleid.apple.com',
    iat, exp (<= 6 months out)}, signed with the APPLE_PRIVATE_KEY (.p8
    contents, from Secret Manager -- never logged, never committed).
    """
```

`APPLE_BUNDLE_ID`, `APPLE_TEAM_ID`, `APPLE_KEY_ID` are non-secret configuration; `APPLE_PRIVATE_KEY` is a secret (see Part J).

## Part C — Backend endpoints (recommendation: provider-specific, not one polymorphic endpoint)

**Recommendation, with rationale (per the spec's explicit ask to justify this choice):** two separate endpoints, `POST /api/auth/google/verify` and `POST /api/auth/apple/verify`, plus one narrow Apple-only follow-up `POST /api/auth/apple/link-existing`. This mirrors the existing `/api/auth/email/request` + `/api/auth/email/verify` pattern already established in this file, keeps each request/response shape honest to what that provider actually needs (Apple needs `authorizationCode` + optional name parts on first auth; Google needs neither), and avoids a discriminated-union request body that would need runtime branching to figure out which fields are required — a pattern this codebase doesn't currently use anywhere. A single generic `/api/auth/provider/verify` endpoint was considered and rejected: it would save one route declaration at the cost of a messier request model and no real behavioral simplification, since the verification logic is provider-specific either way.

### C.1 — `POST /api/auth/google/verify`

```python
class GoogleVerifyRequest(BaseModel):
    id_token: str
    nonce: str  # the raw, unhashed nonce the client generated

@router.post("/google/verify")
def google_verify(data: GoogleVerifyRequest, background_tasks: BackgroundTasks):
    try:
        identity = verify_google_id_token(data.id_token, data.nonce)
    except GoogleVerificationError:
        raise HTTPException(401, "Google sign-in could not be verified. Please try again.")
    try:
        resolved = resolve_identity(
            provider="google", provider_subject=identity.sub,
            email=identity.email.strip().lower() if identity.email else None,
            email_verified=identity.email_verified,
        )
    except NoExistingAccount:
        return {"verified": True, "has_account": False}
    except AmbiguousIdentity:
        logger.error("google_verify: ambiguous identity for a verified Google account")
        raise HTTPException(409, "Something went wrong. Please contact support.")
    # ... identical role-branch/session-mint/login-alert logic to email_auth_verify's
    # success path, reusing the SAME follow-up SELECT + mint_session_token calls,
    # factored into a small shared private helper (see Task 3) rather than duplicated
    # a third time once Apple's success path needs the identical branch too.
```

    identity_token: str
    nonce: str
    authorization_code: str | None = None   # present only on first authorization

@router.post("/apple/verify")
def apple_verify(data: AppleVerifyRequest, background_tasks: BackgroundTasks):
    try:
        identity = verify_apple_identity_token(data.identity_token, data.nonce)
    except AppleVerificationError:
        raise HTTPException(401, "Apple sign-in could not be verified. Please try again.")
    try:
        resolved = resolve_identity(
            provider="apple", provider_subject=identity.sub,
            email=identity.email.strip().lower() if identity.email else None,
            email_verified=identity.email_verified,

    except AmbiguousIdentity:

        raise HTTPException(409, "Something went wrong. Please contact support.")
    # On the FIRST successful resolve/link for this (provider, provider_subject) --
    # detected via whether an auth_identities row existed before this call, see
    # Task 3 -- persist data.full_name into provider_metadata and, if
    # data.authorization_code is present, background_tasks.add_task the refresh-
    # token exchange (non-blocking, per apple_auth.py's own docstring above).
    # ... same shared success-branch helper as C.1.

## Part D — Nonce/state/replay-protection design (both providers)

One shared mobile-side helper, `generateAuthNonce()` (Task 5, using `expo-crypto`'s `Crypto.getRandomBytesAsync` + `Crypto.digestStringAsync` for the SHA-256 hash — both new dependencies, neither currently installed): generates a fresh random raw nonce per sign-in attempt (never reused across attempts, never persisted beyond the single in-flight attempt), computes its SHA-256 hex digest, passes the **digest** into the native Google/Apple sign-in call's `nonce` parameter (both SDKs accept a pre-hashed nonce per their respective docs), and sends the **raw** nonce to the backend alongside the resulting token. Both `verify_google_id_token`/`verify_apple_identity_token` independently re-hash the raw nonce and compare against the token's own `nonce` claim, failing closed on any mismatch or absence. This is symmetric across both providers by design — one mobile helper, one comparison idiom on the backend, no per-provider special-casing beyond where each SDK's parameter is actually plumbed in.

## Part K — Error/security behavior matrix (Section 13)

| Condition | Backend response | Notes |
|---|---|---|
| Invalid signature | 401, generic message | Never leak which check failed |
| Expired provider token | 401, generic message | Same generic message as invalid signature — do not distinguish |
| Wrong issuer | 401, generic message | Same |
| Wrong/unapproved audience | 401, generic message | Same — this is the "someone sent a token meant for a different app" case, must not hint that |
| Missing/wrong nonce | 401, generic message | Same |
| Unverified provider email | Falls through to `NoExistingAccount` if no exact-subject-match exists (email_verified=False makes resolve_identity's auto-link path unreachable, per Phase 5's unchanged contract) | Not a distinct error — same shape as "no account" |
| Valid identity, no existing account | 200, `{"verified": true, "has_account": false}` (Google) or `{"verified": true, "has_account": false, "apple_linkable": true}` (Apple) | Never a 404/error — mirrors `email_auth_verify`'s existing pattern exactly |
| Ambiguous AthFuelPath identity | 409, fixed generic message, zero identifying details | Identical to Phase 5's `email_auth_verify` handling |
| Provider identity already linked to another owner | Unreachable by construction — exact-match-first means it always resolves to its one true owner; this phrase in the spec is read as "confirm this can't happen," not a new error path to build |
| Owner already linked to another identity for that provider | Prevented at the DB layer by Task 1's new partial-unique indexes — an attempted second link 409s via the same `"unique"`/`UniqueViolation` race-safety idiom already used throughout this codebase |
| Cancelled Google/Apple login | Mobile-only concern — the native SDK call itself rejects/resolves with a cancellation signal; no backend request is ever sent; no error state to design server-side |
| Network failure | Mobile-only — standard retry-or-user-message UX, no backend design needed |
| Missing email from Apple after first authorization | Handled structurally: `resolve_identity`/`link_identity_to_owner` never require email to be present — Apple's `email: null` on subsequent logins is expected, normal, and already the exact-match-first path's whole purpose (A.2) |

No error response leaks another user's account information anywhere in this table — every failure path returns either a fixed generic string or the same non-enumerating shape `email_auth_verify` already uses.

## Part L — Risks / Blockers

1. **Google library choice is an open decision, not pre-made** (A.4) — `react-native-nitro-google-signin` is recommended but flagged for explicit sign-off before Task 5 begins, given the real cost/maturity tradeoff against `@react-native-google-signin/google-signin`'s paid Credential Manager tier.
2. **Hybrid native-iOS-project state** (A.1) — the committed `ios/` directory means Apple's entitlement may need direct verification/addition there, not just via the Expo config plugin, depending on whether the EAS build profile prebuild-skips iOS. Must be confirmed empirically in Task 5, not assumed.
3. **Apple Sign-In omitted on Android** (A.5) — no Apple-blessed native path exists; this plan recommends omission rather than building a second, structurally different web-based Services-ID flow, since that would be real new scope. Flagged for explicit confirmation, since it's a product-visible decision, not purely technical.
4. **Athlete-side Apple Hide-My-Email linking is out of this plan's scope** (A.6) — the link-existing flow is parent-only, since athletes have no independent OTP-receiving email channel of their own in this architecture. Recorded, not silently expanded to cover.
5. **`apple_refresh_token` storage protection level is a decision point** (A.7) — this plan proposes storing it at the same protection level as every other sensitive column in this database (Cloud SQL encryption at rest, no app-level envelope encryption), since that matches existing precedent; a stricter requirement would be a deliberate scope increase needing explicit sign-off.
6. **Both Google and Apple require a new EAS development build** — this is a real workflow change from anything done in Phases 0-5 (which never touched native modules), and needs to be budgeted into the mobile timeline, not treated as a drop-in code change.
7. **No official single source picks Android's Google Sign-In library for you** (A.4) — the two-library tradeoff is real and current as of this session's research; if either library's landscape changes between this plan's approval and Task 5's actual implementation, that gap should be re-checked, not assumed frozen.
