# Auth v2.1 — Phase 6 (Google + Apple Sign-In) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Revision history:** v1 was reviewed and returned with 10 mandatory corrections (2026-08-24) → v2. v2 was reviewed and returned with 4 further mandatory corrections (2026-08-24, same day): (1) remove the assumption that Google and Apple hash/compare nonces identically — treat each provider's nonce contract as independently unverified until empirically confirmed; (2) do not assume Apple's user identity token is signed with the same algorithm as the developer-built client-secret JWT; (3) make Apple's authorization-code → refresh-token exchange a synchronous, required precondition for a first-time Apple linkage/login, not a background best-effort side effect; (4) add bounded, infrastructure-free cleanup for the new short-lived tables. This is v3, incorporating all of them. Nothing in this phase has been implemented — this remains a plan-only document pending final external review.

**Goal:** Ship Google Sign-In and Sign in with Apple as first-class login methods, both proving identity **server-side** (never trusting a client-supplied email as proof) and both resolving through the existing Phase 5 `resolve_identity()` common resolver into the existing AthFuelPath session mechanism — with no new accounts created (that's Phase 7), no parallel session system, and Apple's Hide My Email / first-authorization-only-data quirks handled explicitly rather than assumed away.

**Architecture (v3):** A server-issued, single-use, short-lived **provider-auth challenge** (`POST /api/auth/provider/challenge`) replaces a mobile-generated nonce as the authoritative replay-protection mechanism, storing the raw issued nonce server-side (not a pre-committed hash — its comparison transform is provider-specific and empirically determined, A.6). Two verification endpoints (`POST /api/auth/google/verify`, `POST /api/auth/apple/verify`) consume a challenge atomically, perform full server-side cryptographic verification of the provider's token — including an algorithm allowlist independently confirmed per provider, never assumed (A.5) — extract the provider's stable subject + verified email (read from the **verified JWT claims**, never from client-supplied fields), and hand that to the *unchanged* `resolve_identity()`. One additive migration (`004`, new file — `003` is production history and is never edited) adds two partial-unique indexes closing the "multiple identities per owner per provider" gap, plus three new small tables: `provider_auth_challenges` (the server-issued nonce/challenge ledger), `apple_provider_credentials` (application-layer-encrypted Apple refresh tokens, separate from `auth_identities`, keyed to it, captured via a **synchronous, required** exchange on first linkage — A.8), and `apple_pending_links` (short-lived server-side state binding an already-verified-but-unlinked Apple identity to the Hide-My-Email secondary-OTP flow). Both new short-lived tables get bounded, infrastructure-free opportunistic cleanup (A.11). A new small resolver-adjacent function, `link_identity_to_owner()`, handles linking a verified-but-unresolved Apple identity to an existing account once OTP proof arrives. Mobile adds a `react-native-nitro-google-signin` (pinned) button and `expo-apple-authentication`'s native Apple button to `app/(auth)/login.tsx` — iOS gets both plus Email; Android gets Google plus Email only, Apple intentionally excluded this phase (not because no path exists, but because the only path — Apple's web/Services-ID flow — brings infrastructure not justified by current requirements).

**Tech Stack:** FastAPI + psycopg3 (Postgres) backend, `google-auth` (Google verification), a JWT/JWKS library for Apple (final pick in Task 1), and Python's `cryptography` package (**already a backend dependency**) for AEAD encryption of Apple refresh tokens — no new crypto library needed. Expo SDK 54 / React Native 0.81 / Expo Router mobile, requiring a new EAS development build.

**Spec:** User's Phase 6 kickoff message plus the 2026-08-24 correction message (10 numbered items) — both referred to throughout as "the spec." Builds on all five prior phase plans in this directory, especially Phase 5's resolver.

**Worktrees:**
- Backend: `~/FuelUpYouth-auth-v2.1`, branch `feature/auth-v2.1` (in sync with `main` at `a4d409c`).
- Mobile: `~/FuelUpYouth_Mobile/fuelup-mobile-auth-v2.1` (confirm sync with mobile `main` at `780a5fb` before Task 5).

**Explicitly out of scope for this phase:** Phase 7 signup/account creation; public signup; Phase 8 athlete invitation codes; Phase 9 forced reauthentication; Phase 10 deletion/revocation behavior itself (only its storage *prerequisite*); refresh tokens for AthFuelPath's own sessions; AthFuelPath session `jti`/general revocation (the new provider-auth challenge ledger is narrowly scoped to provider authentication only — it is not a general session-revocation mechanism); password authentication; Settings → linked-accounts UI; general account-merging UI; unrelated CORS changes; Google Places key cleanup; TeamCoach/admin authentication refactors; unrelated database cleanup; Apple Sign-In on Android (this phase).

### A.4 — Google implementation approach — library decision APPROVED

**Approved: `react-native-nitro-google-signin`, pinned to an exact version (`2.1.0`, the current release as of this session's research — Task 1 re-confirms this is still current at implementation time and pins whatever that confirmed-current version is; never an unbounded `^`/`~` range for a native-module dependency this security-sensitive).** Rationale (per the approval): current Expo documentation supports it; it uses the modern Android Credential Manager path rather than Google's deprecated legacy Android Sign-In SDK; no paid tier is required (unlike `@react-native-google-signin/google-signin`'s Credential Manager support, which is paywalled).

**Client ID architecture — three Google Cloud OAuth client IDs are needed, each for a different purpose:**
- **iOS OAuth client ID** and **Android OAuth client ID + signing SHA-1 fingerprint** — these **register/identify the native app binaries** with Google (app allow-listing, redirect routing). They are not, by themselves, the backend's verification audience.
- **Web/server OAuth client ID** — this is the one used to **configure ID-token issuance**: the mobile SDK is configured with this Web client ID as its `serverClientID`/`webClientId`, which makes the resulting ID token's `aud` claim equal the Web client ID regardless of which platform issued it.

**Backend audience validation (approved design): an allowlist, not a single hardcoded value, but populated with exactly one entry by default.** `GOOGLE_ALLOWED_AUDIENCES` is a configured set (env/Secret-Manager-backed), containing **only the approved AthFuelPath Web/server client ID** at launch. The verification function checks `aud ∈ GOOGLE_ALLOWED_AUDIENCES`, not `aud == <single value>` — this is a set-membership check, deliberately structured as an allowlist so that if implementation-time testing against the actual selected SDK (`react-native-nitro-google-signin` 2.1.0) reveals it legitimately emits a different/additional audience value in some code path, that finding gets reported and the allowlist is deliberately expanded with justification — **the plan does not pre-populate the iOS or Android client IDs into this allowlist speculatively.** Task 2 must include an explicit empirical check (a real device/simulator test token) confirming the actual `aud` value the chosen SDK produces before backend verification code is considered final.

### A.5 — Apple implementation approach

**`expo-apple-authentication`** is iOS-only (`platforms: ['ios', 'tvos', 'expo-go']` per its own source). `signInAsync()` returns `{user, state, fullName, email, realUserStatus, identityToken, authorizationCode}`. Required config: `plugins: ["expo-apple-authentication"]` + `ios.usesAppleSignIn: true` in `app.json`, plus direct verification against the already-committed `ios/` project (A.9).

**App Store Review (Guideline 4.8) — confirmed:** offering a third-party/social login (Google) requires also offering "another login service" meeting three privacy criteria; Sign in with Apple is the only option that satisfies all three by construction, and none of the guideline's exemptions apply here. **Offering Google Sign-In makes offering Apple Sign-In on iOS effectively mandatory for App Store approval.**

**Server-side verification:** Apple's JWKS endpoint is `GET https://appleid.apple.com/auth/keys` (select by `kid`). Required checks: signature, the server-issued challenge's nonce (A.6), `iss == https://appleid.apple.com`, `aud == APPLE_BUNDLE_ID` (`com.fuelupyouth.app` — the native-app audience rule; a Services ID would only apply to a web/Android flow, which this phase doesn't build), `exp`. **Signature algorithm — corrected, not assumed (see A.5's algorithm note below): this plan does not hardcode ES256 for the user identity token based on Apple's client-secret JWT also using EC signing — those are two different tokens with independently-confirmed requirements.**

**Algorithm handling — corrected per the spec's second correction: do not conflate the user identity token's signing algorithm with the developer-built client-secret JWT's algorithm.** These are two structurally different tokens with two independently-determined requirements:
- **The user identity token** (`identityToken`, built by Apple, verified by `verify_apple_identity_token`) — its actual `alg`/JWK key type must be **empirically confirmed at Task 1**, not assumed, by inspecting (a) Apple's live JWKS (`GET https://appleid.apple.com/auth/keys`) for the key types it actually publishes, and (b) the decoded header of a genuine identity token produced by the actual selected native flow (`expo-apple-authentication`'s `signInAsync()` on a real device/simulator build). Only after that confirmation does `verify_apple_identity_token` hardcode an **explicit single-algorithm allowlist** (e.g. `algorithms=["<confirmed-alg>"]` passed to the JWT library — never a wildcard, never trusting the token's own unverified `alg` header to pick the algorithm). The function must reject: `alg=none`; any algorithm not in the confirmed allowlist; a `kid` not present in the current JWKS; a signature that fails verification under the confirmed key; wrong issuer; wrong audience; expiry; nonce mismatch. Each of these is a distinct, independently-tested failure mode (Part H).
- **The developer-built client secret** (`_build_apple_client_secret()`, built by *this codebase*, sent *to* Apple) — this one genuinely and explicitly requires ES256 per Apple's own REST API documentation (A.5, revocation prerequisite section) — that requirement is Apple's stated contract for what *we* must produce, not evidence about what algorithm Apple uses to sign tokens *it* issues. `_build_apple_client_secret()` keeps its ES256 signing exactly as designed; **the two functions must never share an algorithm constant or any other conflated assumption** — Task 1 defines them as two textually and conceptually separate pieces of code, each with its own independently-justified algorithm choice.

**Corrected framing of "first authorization only" (per the spec's correction — three distinct things, not one, must not be conflated):**
1. **Apple's native credential response** (`signInAsync()`'s return value, delivered client-side, never part of any cryptographic proof) — `fullName` is reliably present **only on the very first authorization ever**, for the lifetime of that (Apple ID, app) pairing; on every subsequent sign-in, `credential.fullName` is `null`. This is a one-time, unrecoverable data point if not captured at that exact moment.
2. **`credential.email`** (also from the native response, also client-supplied, also **never trusted as authentication evidence**) similarly may be `null` on subsequent logins — but this is not the same claim as "Apple's email disappears forever." It only means the native SDK stops repeating it in its own local response object.
3. **The verified Apple identity token's own `email`/`email_verified` claims** — these come from the cryptographically signed JWT (`verify_apple_identity_token`'s return value), not from the native credential object, and the backend derives its authoritative "what is this user's Apple-associated email, and is it verified" answer **from the token claims, when present in that specific token** — never from `credential.email`. The plan's v1 incorrectly implied both sources behave identically and permanently vanish; this is corrected here.

**Full name is NOT persisted in Phase 6 — reversal from v1, per the spec's minimize-PII-storage correction.** Phase 6 never creates a new AthFuelPath account (that's Phase 7); every successful Google/Apple login in this phase either resolves to an *existing* parent/athlete (who already has a name on file) or goes through the Hide-My-Email link flow to an *existing* parent (same). There is no concrete Phase 6 code path that reads or needs Apple's `fullName`. **This plan does not build storage for it.** If Phase 7 (signup) later needs it, that phase can address the "capture it on first authorization or lose it forever" problem in its own scope — building unused storage for it now would be exactly the kind of unnecessary PII retention the correction asks to avoid.

**Revocation prerequisite (Phase 10 dependency) — storage design corrected, see A.7.** `POST https://appleid.apple.com/auth/revoke` requires a stored refresh token; the only way to obtain one is exchanging `signInAsync()`'s `authorizationCode` via `POST https://appleid.apple.com/auth/token` at first authorization — there is no "look up tokens after the fact" API, so this exchange must happen now even though the revoke call itself is Phase 10's job.

### A.6 — Nonce/replay protection — server-issued challenge, with the per-provider comparison transform corrected (not assumed identical)

**v2's design assumed both Google and Apple hash the issued nonce with SHA-256 before embedding it in the token, and stored only that hash server-side. This is rejected per the spec's third-round correction: the exact transform each provider's chosen mobile SDK applies to the nonce — what it accepts as input, and what value actually lands in the verified token's `nonce` claim — has not been empirically confirmed for either provider, and must not be assumed identical (or assumed at all) merely for implementation symmetry.**

**Corrected design principle:** the server-issued challenge stores the **raw nonce value itself**, not a pre-committed hash of it under an assumed transform. This is what makes correctness possible regardless of which transform each provider turns out to require — the raw value can be compared directly, or hashed on the fly with whatever algorithm Task 1 empirically confirms, without needing to have guessed correctly on the day the challenge was issued. (A nonce is a replay-protection marker compared against a value embedded in an already cryptographically-signed and independently-verified token — it does not grant access to anything by itself the way an OTP code does, so storing it in plaintext server-side, for a short, single-use, auto-cleaned lifetime (A.11), is an acceptable and deliberately more flexible choice than committing to an unverified hash transform.)

**New endpoint: `POST /api/auth/provider/challenge`**
```python
class ProviderChallengeRequest(BaseModel):
    provider: str  # "google" | "apple"

@router.post("/provider/challenge")
def provider_challenge(data: ProviderChallengeRequest):
    if data.provider not in ("google", "apple"):
        raise HTTPException(422, "Unsupported provider.")
    _cleanup_expired_provider_auth_state()  # opportunistic, bounded — A.11
    raw_nonce = secrets.token_urlsafe(32)          # cryptographically random, server-generated
    challenge_id = secrets.token_urlsafe(24)        # opaque handle returned to the client
    conn = get_conn()
    try:
        conn.execute(
            "INSERT INTO provider_auth_challenges (challenge_id, provider, raw_nonce, expires_at) "
            "VALUES (%s, %s, %s, %s)",
            (challenge_id, data.provider, raw_nonce, <now + 5 minutes>),
        )
        conn.commit()
    finally:
        conn.close()
    return {"challenge_id": challenge_id, "nonce": raw_nonce}
```
No user identity is assumed or referenced at this point — the row is purely `{challenge_id, provider, raw_nonce, expires_at, consumed_at NULL, created_at}` (see migration, Part E).

**Required empirical validation task, before either provider's comparison function is considered final (Task 1, blocking — see Part L):**
1. **Google, via `react-native-nitro-google-signin` (the approved, pinned SDK):** produce one genuine sign-in on a real device/simulator dev build, passing the server-issued `raw_nonce` into whatever parameter the library's actual `configure()`/sign-in call exposes for this purpose. Decode the resulting real ID token's `nonce` claim. Determine and document: does the claim equal `raw_nonce` verbatim, or `sha256(raw_nonce)`, or some other transform this specific library applies? Write `_google_nonce_matches(raw_nonce: str, token_nonce_claim: str) -> bool` to encode exactly that confirmed transform — nothing else.
2. **Apple, via `expo-apple-authentication`:** produce one genuine `signInAsync()` call on a real iOS device/simulator, passing `raw_nonce` as the `nonce` option. Decode the resulting real identity token's `nonce` claim. Determine and document the actual transform (Apple's own docs describe a SHA-256 pre-hash for *some* of Apple's web/JS flows, but this must be confirmed for `expo-apple-authentication`'s specific native code path, not assumed to carry over). Write `_apple_nonce_matches(raw_nonce: str, token_nonce_claim: str) -> bool` to encode exactly that confirmed transform.
3. **Two independent comparison functions are expected, not one shared implementation** — if empirical testing shows both providers happen to use the same transform, that's a discovered fact to document, not a design assumption to build in advance. Task 1's implementation report must state, for each provider, the exact input value passed to the SDK, the exact value found in the resulting real token, and the exact transform (if any) connecting them — with the real (redacted-of-PII) token payloads or a clear description of the observed values as evidence, not just an assertion that verification "works."
4. **At no point does the backend trust a nonce value supplied independently by the mobile client outside of this flow** — the only nonce-adjacent value mobile ever sends back is the provider's signed token itself (whose `nonce` claim is cryptographically bound to that specific token by the provider, not re-assertable by the client) plus the `challenge_id` handle. Mobile never sends a bare "trust me, this was the nonce" value that the backend compares against anything.

**Verification endpoints (`google/verify`, `apple/verify`) now require `challenge_id`, and MUST, in order:**
1. Atomically consume the challenge: `UPDATE provider_auth_challenges SET consumed_at = now() WHERE challenge_id = %s AND provider = %s AND consumed_at IS NULL AND expires_at > now() RETURNING raw_nonce` — the exact same atomic-consumption idiom this codebase already uses for OTP codes (`otp_auth.py`'s `UPDATE ... WHERE used = 0 RETURNING id`). If this returns no row (challenge doesn't exist, wrong provider, already consumed, or expired), fail closed with 401 — no token verification is even attempted.
2. Verify the provider token's signature/issuer/audience/expiry (Parts B.1/B.2, including the algorithm-allowlist correction, A.5).
3. Verify the token's `nonce` claim matches the retrieved `raw_nonce`, using that **provider's own confirmed comparison function** (`_google_nonce_matches`/`_apple_nonce_matches`) — never a shared, assumed-identical comparison.
4. Only if all of 1-3 pass, proceed to `resolve_identity()`.

**A successfully consumed challenge cannot authenticate a second request** — the atomic `WHERE consumed_at IS NULL` guarantees this at the database layer, independent of anything the mobile client does or doesn't do correctly. Required tests (Part H): nonce mismatch fails (for each provider's actual comparison function); a consumed challenge cannot be replayed against a second verification attempt, even with a technically-valid provider token.

**Apple's `state` parameter — supplementary only, not a replacement.** `signInAsync()` accepts an optional `state` string; this plan sets it to the `challenge_id`, giving Apple's own response an additional binding back to the specific challenge that was issued. This is defense-in-depth, not the primary mechanism — the real security property rests on step 1's atomic, database-enforced single-use consumption plus step 3's cryptographic nonce-claim comparison.

**Scope boundary, restated:** this challenge ledger is narrowly for provider-authentication replay protection. It is not a session token, carries no `jti`/revocation semantics for AthFuelPath's own sessions, and `mint_session_token`/`session_auth.py` are untouched.

### A.7 — Apple refresh-token storage — REDESIGNED with application-layer encryption (v1's plaintext-column design is rejected)

**v1 proposed a plaintext `apple_refresh_token TEXT` column on `auth_identities`, relying only on Cloud SQL's disk-level encryption. This is rejected per the spec's correction.**

**v2 design:**
- **New table, separate from `auth_identities`, keyed to it**: `apple_provider_credentials (id, auth_identity_id UNIQUE REFERENCES auth_identities(id) ON DELETE CASCADE, encrypted_refresh_token BYTEA NOT NULL, encryption_nonce BYTEA NOT NULL, created_at)`. One row per Apple identity that has a captured refresh token; `UNIQUE(auth_identity_id)` enforces at most one credential row per identity.
- **Encryption: AES-256-GCM via Python's `cryptography` package** (`cryptography.hazmat.primitives.ciphers.aead.AESGCM`) — already a backend dependency, no new library. AEAD (authenticated encryption with associated data) is used, not a bare cipher, so tampering with stored ciphertext is detectable, not just confidentiality-protected. A fresh random 96-bit nonce is generated per encryption (`os.urandom(12)`), stored alongside the ciphertext (nonces for AEAD are not secret, only the key is).
- **New service module**: `api/services/provider_credential_crypto.py`:
  ```python
  def encrypt_refresh_token(plaintext: str) -> tuple[bytes, bytes]:
      """Returns (ciphertext, nonce). Uses AESGCM with
      PROVIDER_CREDENTIAL_ENCRYPTION_KEY (32 raw bytes, from Secret Manager)."""

  def decrypt_refresh_token(ciphertext: bytes, nonce: bytes) -> str:
      """Decrypts; raises on any tampering (AEAD tag mismatch) rather than
      silently returning corrupted data."""
  ```
- **Key management**: `PROVIDER_CREDENTIAL_ENCRYPTION_KEY` — a dedicated 256-bit key, **separate from `APP_SESSION_SECRET`**, generated once, stored **only** in Google Secret Manager, attached to the Cloud Run service as a secret (same mechanism `APP_SESSION_SECRET`/`GMAIL_APP_PASSWORD` already use — no new infrastructure pattern, just a new secret name). Never committed, never returned to mobile, never logged.
- **Logging discipline, made explicit as a hard constraint for Task 2's implementation**: refresh tokens, access tokens, authorization codes, the Apple private key, and any decrypted provider credential value must never appear in a log line, an exception message, or a `logger.error`/`logger.warning` call anywhere in this phase's code. Code review (Task 2's quality-review pass) must specifically check every new log statement against this list.

**What's stored, and only what Phase 10 actually needs:** the encrypted refresh token (the one thing `POST /auth/revoke` requires that can only be obtained once, at first authorization) and nothing else — no access token (short-lived, not needed for a future revoke call per Apple's own docs, which accept either token type but a refresh token is the durable one worth keeping), no raw authorization code (single-use and already consumed by the exchange), no scopes/metadata beyond what's structurally required.

**Subject-binding check on the exchange response (per the spec's third-round correction) — see A.8 for full synchronous-exchange design.** Apple's `/auth/token` response includes its own `id_token`. Before trusting and storing the returned `refresh_token`, `exchange_authorization_code_for_refresh_token()`'s caller must decode that response `id_token` (a lightweight claims-read, not a second full JWKS-signature-verification pass — the call itself was made directly to Apple over HTTPS with our own `client_secret`, so the response's authenticity rests on transport + our own outbound authentication, not a second independent signature check) and confirm its `sub` and `aud` match the already-verified identity's `sub` and `APPLE_BUNDLE_ID` exactly, before the refresh token is encrypted and persisted. A mismatch here must never happen under correct operation — it exists as a hard-fail sanity check (reject, do not store, surface as an exchange failure per A.8) against any conceivable response-substitution class of bug, not as a normally-expected branch.

### A.8 — Apple Hide My Email first-link design, and synchronous refresh-token capture (corrected, third round)

**v1's design had `apple/link-existing` re-verify the raw Apple identity token from scratch on the second call.** v2 introduced a **short-lived server-side pending-link record** so the already-verified social identity stays securely bound server-side while the user completes the secondary OTP step. **v2 also made the Phase-10 refresh-token exchange a background, best-effort `background_tasks.add_task` — this is corrected here: the exchange is now synchronous and, for any first-time linkage, required.** A login/link is not considered complete if the exchange was needed and failed.

**Corrected rule, stated once and applied everywhere below:** for any successfully-verified Apple identity, before treating a login or link as complete, the backend checks whether `apple_provider_credentials` already has a row for that identity:
- **Already has a stored credential:** no exchange is performed, even if the request happens to carry a fresh `authorization_code` (Apple provides one on every `signInAsync()` call, not just the first — a later login does not need to replace an already-stored, still-usable credential merely because another code arrived incidentally).
- **No stored credential yet (true first linkage for this `(provider, provider_subject)`):** a valid `authorization_code` is **required** in the request. The exchange (`exchange_authorization_code_for_refresh_token`, A.7/B.2) is performed **synchronously, inline, before the response is returned** — not backgrounded. If the request is missing `authorization_code` in this situation, or the exchange itself fails for any reason (network error, Apple-side error, the A.7 subject-binding check failing), **the endpoint does not return a successful result**: no session is minted, no `has_account`/`apple_linkable` success signal is returned, and the response must not claim the Phase-10 prerequisite was captured. This is a deliberate behavior change from "login always succeeds if the identity token itself verified" — for a genuinely first-time Apple identity, capturing the revocation prerequisite is now a hard precondition of considering that first login/link successful, not a nice-to-have side effect.
- **Failure response:** `502` with a generic message ("Apple sign-in could not be completed. Please try again.") — distinct from `401` (the identity token itself failed to verify — a different failure class) and `409` (ambiguous existing-owner match). `502` is used because this specific failure mode is "we verified you, but our required downstream call to Apple's own token endpoint failed" — an upstream-dependency failure, not an authentication failure on the caller's part.

**Flow (Google/Apple `verify`, updated):**
1. Mobile: `POST /api/auth/provider/challenge {provider: "apple"}` → `{challenge_id, nonce}` (A.6).
2. Mobile: native `signInAsync()` with that nonce (transform per A.6's empirical finding), `state: challenge_id`.
3. Mobile: `POST /api/auth/apple/verify {challenge_id, identity_token, authorization_code}` — mobile always includes `authorization_code` when Apple provides one (Task 1 confirms empirically whether it's genuinely present on every call or only sometimes, per A.6's same "verify, don't assume" discipline applied here too — the backend's required-ness check is driven by whether a stored credential already exists, not by a blanket assumption about Apple's per-call behavior).
4. Backend: atomically consumes the challenge (A.6) → verifies the Apple identity token, confirmed algorithm allowlist (A.5) → calls `resolve_identity(provider="apple", provider_subject=identity.sub, email=identity.email, email_verified=identity.email_verified)`.
   - **Resolves to an existing owner:** look up the resolved identity's `auth_identities.id` (a follow-up `SELECT`, matching this codebase's established "resolver returns IDs, route does its own row lookup" pattern) and check `apple_provider_credentials` for an existing row. If none exists, `authorization_code` is required and the exchange happens synchronously now, per the corrected rule above (failure → 502, no session). If it succeeds (or a credential already existed), proceed to mint the session exactly as Google's success path (shared helper, Part F).
   - **`NoExistingAccount`:** the Hide-My-Email case — see below.
   - **`AmbiguousIdentity`:** 409, fixed generic message, identical to Phase 5's existing handling.

**Hide-My-Email pending-link path (`NoExistingAccount`), corrected exchange ordering:**

Per the spec's correction, the exchange happens **before** the pending record is created, not deferred into it as an optional field populated "if present": if `authorization_code` is present, the backend performs the synchronous exchange **now** (same 502-on-failure behavior — if the exchange fails, the whole `apple/verify` call fails, and no pending-link record is created at all, since a pending link that promises Phase-10 readiness but doesn't actually have working credential material would be worse than not offering the link-existing path this attempt). If the exchange succeeds, its encrypted result is stored **directly in the pending-link record** (not deferred, not backgrounded) alongside the already-verified `provider_subject`:

`apple_pending_links (id, pending_link_id UNIQUE, provider_subject, email_from_token, email_verified_from_token, encrypted_refresh_token BYTEA NULL, encryption_nonce BYTEA NULL, expires_at, consumed_at NULL, created_at)`.

(`encrypted_refresh_token` remains nullable at the schema level only to cover the case where Apple genuinely didn't supply an `authorization_code` at all on this specific call — per A.6's discipline, whether that's a realistic case is confirmed empirically at Task 1, not assumed; it is not nullable-by-design for "we chose to defer it," which was v2's now-corrected behavior.)

Returns `{"verified": true, "has_account": false, "apple_linkable": true, "pending_link_id": <opaque id>}`. `expires_at` is short (10-15 minutes).

**Remaining steps (5-7), unchanged in shape from v2, restated for completeness:**

5. Mobile: calls the existing, unchanged `POST /api/auth/email/request` with the user-typed existing-account email.
6. Mobile: `POST /api/auth/apple/link-existing {pending_link_id, email, code}`.
7. Backend, **transactionally** (one DB transaction, fail closed on any conflict):
   - Look up the pending-link row: must exist, `consumed_at IS NULL`, `expires_at > now()`, else 401/expired.
   - `verify_otp_code(email, code)`. On failure, 401, the pending-link row is left unconsumed (retriable before expiry) — no linkage, no account touched.
   - Resolve `email` to exactly one existing parent (shared `_resolve_exactly_one_owner()` helper) — 0 or 2+ matches fails closed.
   - Atomically consume the pending-link row and, in the same transaction, call `link_identity_to_owner(provider="apple", provider_subject=<from the pending record>, parent_id=<resolved>)`, and if the pending record carried an already-exchanged encrypted refresh token, insert it into `apple_provider_credentials` keyed to the newly-created `auth_identities` row (a straight copy — no second exchange, since it already happened synchronously in step 4). Any uniqueness conflict rolls back the entire transaction.
   - Mint the session exactly as the parent branch always does.

**This satisfies every explicit constraint the spec restates:** the stable Apple `sub` becomes authoritative only after real linkage; typing an email alone can never link anything; the already-verified social identity stays server-side-bound; the Phase-10 prerequisite, when required, is captured synchronously and the flow fails honestly (never silently, never falsely claiming success) if that capture fails; the final linkage is one transaction, fail-closed on conflicts; no AthFuelPath account is ever created.

**Athlete accounts remain explicitly out of this linking flow**, as in v1 — an athlete has no independent OTP-receiving email channel of their own in this architecture. Recorded as a known scope boundary (Part L), not silently expanded.

### A.11 — Expired short-lived record cleanup (new, per the spec's fourth correction)

`provider_auth_challenges` and `apple_pending_links` are both short-lived (5-minute and 10-15-minute TTLs respectively) but the latter can carry encrypted Apple refresh-token material for an abandoned flow — that must not linger indefinitely just because no one built cleanup. **No scheduler, cron job, or other new infrastructure is introduced** — cleanup is opportunistic, piggybacked on an existing high-traffic entry point into this exact subsystem:

```python
def _cleanup_expired_provider_auth_state():
    """Opportunistic, bounded cleanup — no scheduler needed. Called at the
    top of provider_challenge(), the highest-traffic entry point into this
    subsystem, so stale rows never accumulate indefinitely even under
    normal usage alone. Cheap at the row counts these tables will ever
    realistically hold (5-15 minute TTLs mean no large backlog even
    without this, but expired apple_pending_links rows can hold encrypted
    Apple refresh-token material, which must not be left indefinitely)."""
    conn = get_conn()
    try:
        conn.execute("DELETE FROM provider_auth_challenges WHERE expires_at < now()")
        conn.execute("DELETE FROM apple_pending_links WHERE expires_at < now() AND consumed_at IS NULL")
        conn.commit()
    finally:
        conn.close()
```

Called at the start of `provider_challenge()` (A.6) — every new sign-in attempt opportunistically sweeps stale rows from both tables first. This is narrowly scoped to exactly these two Phase 6 temporary tables — it is not a general-purpose scheduled-cleanup mechanism, and does not touch `otp_codes` or any other existing table's own (already-established, unrelated) lifecycle. Consumed `apple_pending_links` rows (successfully completed links) are intentionally left alone by this cleanup — they're inert once consumed, and deleting them isn't necessary for the encrypted-material-hygiene concern this cleanup exists to address; if retaining them indefinitely becomes a concern later, that's a separate, smaller follow-up, not blocking Phase 6.

Migration `004` (Part E) adds plain btree indexes on `expires_at` for both tables so this cleanup stays cheap regardless of future volume.

### B.2 — Apple

```python
# api/services/apple_auth.py (new)

@dataclass
class VerifiedAppleIdentity:
    sub: str
    email: str | None            # from the verified TOKEN claims, never credential.email
    email_verified: bool

class AppleVerificationError(Exception):
    """Signature/issuer/audience/expiry/nonce check failed."""

def verify_apple_identity_token(identity_token: str, raw_challenge_nonce: str) -> VerifiedAppleIdentity:
    """
    Fetches/caches Apple's JWKS, selects the key matching the token's kid.
    Verifies signature against an EXPLICIT, empirically-confirmed algorithm
    allowlist (Task 1 confirms the real alg/key type from a genuine token
    and Apple's live JWKS before this is finalized -- see A.5 -- never
    assumed to be ES256 just because the unrelated client-secret JWT uses
    that algorithm). Rejects alg=none, any algorithm outside the confirmed
    allowlist, and any kid not present in the current JWKS. Verifies
    iss == 'https://appleid.apple.com', aud == APPLE_BUNDLE_ID, exp, and
    that the token's 'nonce' claim matches raw_challenge_nonce via
    _apple_nonce_matches() -- the transform empirically confirmed at
    Task 1 for expo-apple-authentication's specific native flow, not
    assumed to match Google's transform. Raises AppleVerificationError on
    any failure. Returns sub/email/email_verified read from the verified
    token only -- NEVER from the client-supplied credential.email/fullName
    fields, which this function doesn't even accept as input.
    """

async def exchange_authorization_code_for_refresh_token(authorization_code: str, expected_sub: str) -> str:
    """
    SYNCHRONOUS, required for any first-time linkage for a given
    (provider, provider_subject) -- see A.8 for the full corrected
    (non-backgrounded) design. POSTs to https://appleid.apple.com/auth/token
    with client_id=APPLE_BUNDLE_ID, client_secret=<freshly-signed JWT,
    built per-call, never a stored static string -- see
    _build_apple_client_secret>, code=authorization_code,
    grant_type=authorization_code. Decodes the response's own id_token and
    confirms its sub == expected_sub and aud == APPLE_BUNDLE_ID (A.7's
    subject-binding check) before returning anything -- raises
    AppleVerificationError on a mismatch, never silently substituting.
    Returns the raw refresh_token (caller encrypts before storage, per
    A.7 -- this function never persists anything itself, and never logs
    the returned token or the raw authorization_code). Raises on any
    failure -- the caller (A.8) must treat that as blocking a first-time
    login/link, not a background side effect to shrug off.
    """

def _build_apple_client_secret() -> str:
    """
    Builds a fresh ES256-signed JWT client_secret for EACH call needing
    one (token exchange today; Phase 10's eventual revoke call later) --
    never stored as a static long-lived string. header {alg: ES256,
    kid: APPLE_KEY_ID}; payload {iss: APPLE_TEAM_ID, sub: APPLE_BUNDLE_ID,
    aud: 'https://appleid.apple.com', iat, exp <= 6 months out}; signed
    with APPLE_PRIVATE_KEY (the .p8 contents, read from Secret Manager at
    call time, never logged, never cached to disk).
    """
```

class GoogleVerifyRequest(BaseModel):

### C.3 — `POST /api/auth/apple/verify`

```python
class AppleVerifyRequest(BaseModel):
    challenge_id: str
    identity_token: str
    authorization_code: str | None = None   # required in practice whenever no stored
                                             # credential exists yet for this identity --
                                             # see the synchronous-exchange logic below

@router.post("/apple/verify")
def apple_verify(data: AppleVerifyRequest, background_tasks: BackgroundTasks):
    raw_nonce = _consume_challenge(data.challenge_id, provider="apple")
    try:
        identity = verify_apple_identity_token(data.identity_token, raw_nonce)  # uses _apple_nonce_matches()
    except AppleVerificationError:
        raise HTTPException(401, "Apple sign-in could not be verified. Please try again.")
    try:
        resolved = resolve_identity(
            provider="apple", provider_subject=identity.sub,
            email=identity.email.strip().lower() if identity.email else None,
            email_verified=identity.email_verified,
        )
    except NoExistingAccount:
        # Hide-My-Email path. Exchange BEFORE creating the pending record --
        # corrected per A.8: synchronous, and if authorization_code is
        # present but the exchange fails, the whole request fails (502),
        # no pending link is created promising a capability it doesn't have.
        encrypted_credential = None
        if data.authorization_code:
            try:
                raw_refresh_token = await exchange_authorization_code_for_refresh_token(
                    data.authorization_code, expected_sub=identity.sub,
                )
                encrypted_credential = encrypt_refresh_token(raw_refresh_token)
            except AppleVerificationError:
                raise HTTPException(502, "Apple sign-in could not be completed. Please try again.")
        pending_link_id = _create_apple_pending_link(
            provider_subject=identity.sub, email_from_token=identity.email,
            email_verified_from_token=identity.email_verified,
            encrypted_credential=encrypted_credential,
        )
        return {"verified": True, "has_account": False, "apple_linkable": True, "pending_link_id": pending_link_id}
    except AmbiguousIdentity:
        logger.error("apple_verify: ambiguous identity for a verified Apple account")
        raise HTTPException(409, "Something went wrong. Please contact support.")

    # Resolved to an existing owner. Synchronous, required exchange ONLY if
    # no credential is already stored for this exact identity -- corrected
    # per A.8, no longer a background_tasks side effect.
    auth_identity_id = _lookup_auth_identity_id(provider="apple", provider_subject=identity.sub)
    if not _has_stored_apple_credential(auth_identity_id):
        if not data.authorization_code:
            raise HTTPException(502, "Apple sign-in could not be completed. Please try again.")
        try:
            raw_refresh_token = await exchange_authorization_code_for_refresh_token(
                data.authorization_code, expected_sub=identity.sub,
            )
            _store_apple_credential(auth_identity_id, encrypt_refresh_token(raw_refresh_token))
        except AppleVerificationError:
            raise HTTPException(502, "Apple sign-in could not be completed. Please try again.")
    return _mint_session_for_resolved_identity(resolved)
```

### C.4 — `POST /api/auth/apple/link-existing`

```python
class AppleLinkExistingRequest(BaseModel):
    pending_link_id: str
    email: str    # the EXISTING AthFuelPath account's email, typed by the user
    code: str     # the OTP just sent to that email via the existing /email/request

@router.post("/apple/link-existing")
def apple_link_existing(data: AppleLinkExistingRequest, background_tasks: BackgroundTasks):
    email = data.email.strip().lower()
    if not verify_otp_code(email, data.code.strip()):
        raise HTTPException(401, "Invalid or expired code. Please request a new one.")
    conn = get_conn()
    try:
        pending = conn.execute(
            "SELECT * FROM apple_pending_links WHERE pending_link_id = %s "
            "AND consumed_at IS NULL AND expires_at > now()", (data.pending_link_id,),
        ).fetchone()
        if not pending:
            raise HTTPException(401, "This sign-in attempt has expired. Please try Continue with Apple again.")
        try:
            parent_id = _resolve_exactly_one_parent_owner(email)  # shared helper, Part F
        except (NoExistingAccount, AmbiguousIdentity):
            raise HTTPException(401, "We couldn't verify that account. Please check the email and try again.")
        # Transactional: consume pending link + create identity + (optionally)
        # persist the encrypted credential, all in one transaction. Any
        # uniqueness conflict rolls back everything.
        resolved = _consume_pending_link_and_create_apple_identity(conn, pending, parent_id)
    finally:
        conn.close()
    return _mint_session_for_resolved_identity(resolved)
```

## Part K — Error/security behavior matrix

| Condition | Backend response |
|---|---|
| Invalid signature / unconfirmed or disallowed algorithm / unknown `kid` / expired token / wrong issuer / wrong audience / nonce mismatch (per that provider's own confirmed comparison function) | 401, identical generic message across all of these — never hints which check failed |
| Challenge missing/wrong-provider/expired/already-consumed | 401, generic message, before any token verification is even attempted |
| Unverified provider email | Falls through to `NoExistingAccount` (unreachable auto-link path) — not a distinct error shape |
| Valid identity, no existing account | 200, `{"verified": true, "has_account": false}` (Google) / `{..., "apple_linkable": true, "pending_link_id": ...}` (Apple) — never a 404/error |
| Ambiguous AthFuelPath identity | 409, fixed generic message, zero identifying details |
| Provider identity already linked to another owner | Unreachable by construction (exact-match-first) |
| Owner already linked to another identity for that provider | Prevented at the DB layer by Task 1's new partial-unique indexes, same `UniqueViolation` race-safety idiom used throughout |
| **First-time Apple linkage (no stored credential yet) missing `authorization_code`, or the synchronous exchange with Apple fails, or the exchange response's subject-binding check fails** | **502, generic message — distinct from 401 (identity token itself verified fine; this is a required downstream step failing) — no session minted, no pending-link row created, nothing claims the Phase-10 prerequisite was captured (A.8)** |
| Subsequent Apple login where a valid stored credential already exists | No exchange attempted at all, regardless of whether `authorization_code` is present in the request — proceeds straight to session minting |
| Cancelled Google/Apple login | Mobile-only — no backend request sent |
| Network failure | Mobile-only |
| Missing email from Apple's native credential on a subsequent login | Not an error — expected/normal; backend uses the token's own claims when present (A.5) |
| Expired/consumed Apple pending-link | 401, generic "please try again" message |
| OTP invalid during Hide-My-Email link | 401, pending-link row left unconsumed and retriable until its own expiry |

No error response leaks another user's account information anywhere in this table.

## Part L — Risks / Blockers

1. **Three empirical validations are hard blockers on finalizing verification code, not optional nice-to-haves** (A.5, A.6): (a) Google's actual `aud` value from `react-native-nitro-google-signin` 2.1.0; (b) each provider's actual nonce-input/nonce-claim transform (`_google_nonce_matches`/`_apple_nonce_matches`), confirmed independently, never assumed shared; (c) Apple's actual identity-token signing algorithm and key type, confirmed against a live JWKS fetch and a genuine token's decoded header, never assumed to match the unrelated client-secret JWT's ES256 requirement. Task 1's implementation report must document all three with real evidence before the corresponding verification functions are considered final.
2. **`ios/` native project non-destructive-change process** (A.9) is a real, investigation-gated step, not a rubber stamp — must be done and reported before any Apple/Google native config is committed.
3. **Athlete-side Apple Hide-My-Email linking remains out of this plan's scope** (A.8) — recorded, not silently expanded.
4. **Both Google and Apple require a new EAS development build** — a real workflow change from Phases 0-5, must be budgeted into the mobile timeline.
5. **The encryption key rotation story is not designed in this phase** — `PROVIDER_CREDENTIAL_ENCRYPTION_KEY` is provisioned once; if it ever needs rotation, every existing `apple_provider_credentials` row would need re-encryption. Not a Phase 6 blocker (no rows exist yet), but worth a forward-looking note for whoever eventually owns Phase 10.
6. **`react-native-nitro-google-signin`'s exact pinned version must be re-confirmed current at actual implementation time** (A.4) — this plan pins `2.1.0` based on this session's research; if time has passed before Task 5 begins, re-verify before pinning blindly.
7. **Whether Apple genuinely returns `authorization_code` on every `signInAsync()` call (not just first authorization) is itself empirically unconfirmed** (A.8) — the backend's required-ness logic is deliberately driven by "does a stored credential already exist," not by a blanket assumption about Apple's per-call behavior, specifically so this uncertainty doesn't need to be resolved correctly in advance to be safe — but Task 1 should still confirm it, since it affects whether mobile can always safely include the field.
