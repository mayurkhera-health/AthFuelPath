## Approved Product Decisions in v2.1

1. **Athlete age range is 13–17.** Treat conflicting 9–17 documentation as stale and update it where encountered in auth-related documentation.
2. **Full session revocation is deferred to P1.** Do not add a general `jti`/revocation framework in this P0 authentication feature. Remove the P0 promise of a "Revoke Athlete Access" control. Apple authorization revocation on account deletion remains required because it is provider-specific deletion behavior.
3. **Cloud Run + Cloud SQL/PostgreSQL is the canonical production architecture.** Fly.io is rollback/history only and is not an active deployment target for current `main`.
4. **Athlete invitation MVP uses a short-lived, single-use invitation code generated by the authenticated parent.** No parent-email lookup, sibling list, universal-link dependency, or email invitation is required for this MVP.
5. **Authentication scope stays narrow.** Authorization cleanup, Google Places key restrictions, CORS hardening, and other unrelated audit findings are separate workstreams unless directly required by this authentication implementation.

## Part 1 — Corrections to factual claims in the spec

These are places where v1 asserts something about the current system that is wrong. A developer budgeting from the spec as written will under- or over-estimate the work.

### §2 — Correct as written. Update the README instead.

The spec says bearer tokens already exist. They do: `services/api.ts:24–29` reads `sessionToken` from the auth store and sets `Authorization: Bearer` on every request.

**But** the mobile `README.md` has a section headed **"No JWT / no bearer tokens"** stating the opposite. That section is stale and actively misleading. Delete it.

### §4 — "Reuse the existing OTP infrastructure" understates the work

`otp_codes` is keyed on `parent_id` (`api/routes/parents.py:101`, confirmed by the FK list in `api/routes/admin.py:46`). Consequences the spec doesn't acknowledge:

- An OTP **cannot** be issued to an athlete — §18 requires it.
- An OTP **cannot** be issued to an email with no account — §7 requires exactly that.
- `verify_otp` (`parents.py:112`) returns parent + athletes and **no session token**, so §27's contract is new behaviour, not a rename.

**Edit §4 to read:** rekey `otp_codes` on normalized email; add `attempts` and `consumed_at` columns. Note that `api/services/db_migrations.py` already runs additive idempotent migrations at startup — add `_migrate_otp_codes_to_email()` there.

### §23 — "The existing backend already implements a 60-second resend guard and code expiry"

True (`parents.py:88–95`), but the same block has two defects the spec should name:

- Code generated with `random.randint` (`parents.py:97`) — not cryptographically secure, contradicting §23's own requirement. Fix: `secrets.randbelow(1_000_000)`.
- No attempt limit anywhere in `verify_otp`. §24 is fully net-new.

### §29 — Correct, but the spec misses *why* it's the linchpin

`app/_layout.tsx:38–78`. On every launch:

1. `hydrateFromStorage()` reads role, ids, email **and** sessionToken from SecureStore.
2. `AuthGuard` checks `if (!storedEmail) return;` — **the token is never consulted.**
3. It POSTs the stored email to `/api/auth/login` or `/api/parents/login`.
4. The backend mints a fresh token from the email alone.
5. `setSession(...)` overwrites the stored token.

`store/authStore.ts:220` and `:232` make this structural: both hydration branches require `email` to be truthy, so a valid token with no stored email fails to restore.

**Implication for §51:** the 30-day TTL in `session_auth.py` is irrelevant in practice — every cold start reissues. And you **cannot** delete email-only login before `/api/auth/session` exists and `authStore` hydrates on token alone. See Part 3.

### §39 — Overstated. Authorization is ~60% built.

`api/services/session_auth.py` provides `require_session`, `assert_owns_athlete`, `assert_owns_parent`. **23 of 39 route files use them.** The spec implies this is all outstanding work. It isn't — but see the gap in Part 2.

### §44 — `PUBLIC_SIGNUP_ENABLED` exists and has a better checklist than §44 does

`constants/featureFlags.ts:37–41` carries a `PRE-LAUNCH-GATE` comment block colocated with the flag someone will actually flip. Don't replace it — update it to reference the new endpoints. `assertClaimVerified` (`:70–85`) fails closed on the unsafe combination, which is good design; its own comment correctly notes the gate is bypassable and must be backend-enforced.

## Part 2 — Findings the spec does not cover

### 2.1 — The athlete claim screen leaks parent session tokens (SEVERE)

`app/(auth)/athlete-claim.tsx:44` calls `POST /api/auth/login` with the **parent's email**. `api/routes/auth.py:36` responds to that call with:

```json
{ "role": "parent", "parent": {...}, "athletes": [...], "session_token": "<valid 30-day token>" }

```

The screen reads only `data.athletes` and `data.parent.full_name` and discards the token — but the token was minted server-side and sent over the wire. A proxy, a rebuilt IPA, or curl against the same endpoint yields a **working parent bearer token** that passes `require_session` and `assert_owns_parent` on all 23 protected routes.

The audit framed this as "know an email, see the child's profile." It is actually "know an email, hold a parent session for 30 days."

**Add to spec as its own section.** §47 Tests 1 and 4 are the same vulnerability from two screens.

**Immediate mitigation, ahead of the rest of this spec:** a purpose-built lookup endpoint returning `{exists: bool, athletes: [{id, first_name}]}` and no token. ~1 hour.

### 2.2 — Authorization finding — separate P0 workstream, not v2.1 auth scope

`api/routes/meals.py` and `api/routes/meal_plans.py` import no session guard. Every handler takes `athlete_id` straight from the URL:

- `GET /meal-plans/{athlete_id}` — full week
- `PUT` / `DELETE /meal-plans/{athlete_id}/slot`
- `POST /meal-plans/{athlete_id}/log-slot`
- `GET /meals/athlete/{athlete_id}`
- `DELETE /meals/{meal_id}` — no ownership check whatsoever

This was a valid P0 authorization finding in the reviewed snapshot. It is **not part of the v2.1 authentication implementation** and should be handled/verified in the separate authorization workstream rather than reopened here.

**v2.1 scope decision:** ownership/BOLA remediation is a separate P0 authorization workstream. Do not expand this authentication feature to re-audit or refactor unrelated athlete-scoped routes. If current `main` already contains those fixes, leave them untouched here.

> **Note added during v2.1 design intake (2026-08-20):** current `main` already contains this fix — `meals.py` and `meal_plans.py` were protected with `require_session` + `assert_owns_athlete` as part of the earlier Security Hardening Pass 1 (see `docs/cloud-run-security-audit.md`). Per the scope decision immediately above, leave this untouched; it is not re-opened by v2.1.

### 2.3 — No global 401 handling

`services/api.ts:35` throws `ApiError` with a status and nothing else. `app/_layout.tsx:80` signs out on 401/403/404 — but only inside the launch-time revalidation block. A token expiring while the app is open produces failed queries and no sign-out. §10 requires this behaviour; it belongs in the `request()` wrapper, applied globally.

### 2.4 — Full session revocation is deferred to P1

`session_auth.py` currently mints a signed payload with a baked-in `exp` and keeps no server-side session record, so a general "Revoke Athlete Access" control cannot reliably terminate already-issued sessions.

**v2.1 decision:** do **not** add a general `jti` + revocation table as part of this P0 authentication feature. Remove §22's P0 promise of a "Revoke Athlete Access" control and state the current session lifetime explicitly.

General session revocation, "logout all devices," and early invalidation belong to the separate P1 session-management workstream.

**Exception:** Sign in with Apple authorization must still be revoked when the user deletes their AthFuelPath account, because that is provider-specific account-deletion behavior rather than general AthFuelPath session revocation.


### 2.5 — Enumeration leaks are in the UI copy, not just the API

- `app/(auth)/login.tsx:33` surfaces the raw backend message: "No account found with that email address." (`auth.py`, `parents.py:79`)
- `app/(auth)/athlete-claim.tsx:47,68` — "No parent account was found for that email."

§7 forbids exactly this. Both screens need neutral copy **and** the backend needs to stop distinguishing. Add a §7 sub-item: "always generate, always send, always accept a correct code, then branch" — otherwise timing and mail delivery leak existence regardless of the copy.

### 2.6 — PII disclosure in the claim pick-list

After one email lookup, `athlete-claim.tsx` renders the parent's `full_name` plus every athlete's `first_name` and `age`. Your own flag comments call this "sibling-name exposure." §20's invitation redesign fixes it — say so explicitly in §19.

### 2.6A — Athlete invitation MVP decision: parent-generated short code

§19/§20's invitation redesign is approved, but v2.1 chooses one concrete MVP delivery mechanism.

**Flow:**

1. An authenticated parent selects a specific athlete in AthFuelPath.
2. Backend generates a random, short-lived, single-use invitation code bound to that `parent_id` + `athlete_id`.
3. Parent gives the code directly to the athlete during device handoff.
4. Athlete authenticates with Apple, Google, or verified email.
5. Athlete enters the invitation code.
6. Backend verifies the authenticated identity plus the invitation code and links that identity to exactly that athlete profile.
7. Code is consumed and cannot be reused.

**MVP rules:**

- No parent-email lookup.
- No display of parent names, sibling names, or sibling ages before authorization.
- No email invitation dependency.
- No universal/deep-link requirement.
- Invitation code expires after **15 minutes**.
- Invitation code is **single-use**.
- Rate-limit invalid code attempts.
- Do not expose sequential `athlete_id` values as proof of authorization.

### 2.7 — Age range decision: 13–17

The codebase contains stale documentation that conflicts with the enforced backend rule:

| Source Says                   |                                                       |
| ----------------------------- | ----------------------------------------------------- |
| `api/routes/onboarding.py:25` | `13 <= age <= 17`, rejects otherwise                  |
| Mobile `README.md` line 3     | "youth athletes aged 9–17"                            |
| `DESIGN_SYSTEM.md` §7         | "No supplements recommendation for under-18 athletes" |

**v2.1 decision:** AthFuelPath's supported athlete age range for this feature is **13–17**.

Therefore:

- §18 may be implemented for athletes 13–17.
- Do not redesign authentication for under-13 users.
- Update stale auth-related documentation that still says 9–17.
- Do not reopen this as a product question during implementation.


### 2.8 — Missing from §25/§26: nonce, and the multi-audience problem

Neither validation list includes **nonce** — the replay protection. Generate a random nonce client-side, pass `sha256(nonce)` to the provider, verify the claim server-side. Requires `expo-crypto`, which is not in `package.json`.

Google will issue **three** client IDs (iOS, Android, web/server). Audience validation is set membership, not equality. This is the most common day-one implementation error.

### 2.9 — Apple returns the user's name exactly once

First authorization only. If onboarding crashes after that call, the name is unrecoverable except by the user manually removing the app from Settings → Apple ID. **Persist the Apple payload server-side on the first exchange, before any onboarding screen renders.**

Also required and currently absent: `"usesAppleSignIn": true` in `app.json`'s iOS block, plus the capability in the Apple Developer account.

### 2.10 — In-app account deletion is a launch blocker and is in neither §48 nor §49

App Store Guideline 5.1.1(v): if you support account creation, you must support in-app deletion. Apple additionally expects token revocation on deletion for Sign in with Apple. `eas.json` shows `ascAppId: 6782231976`, so this is a live gate, not theoretical.

### 2.11 — The legacy web frontend is never mentioned

`frontend/src/Login.jsx:64` calls `POST /api/parents/login`. §28 removes that route and the web app's login dies silently. The backend has temporary client-split logging (`parents.py:56`, `auth.py:36`, dated 2026-08-19) apparently added to measure this.

**Finish that measurement before scoping.** Zero web traffic → delete `frontend/`. Some traffic → repoint it at `/api/auth/email/*`. Real traffic → Phases 3 and 4 double in size.

### 2.12 — CORS finding — separate security-hardening workstream

`api/main.py:100` sets `allow_origins=["*"]`. The comment at `:101` correctly notes that `allow_credentials=True` with a wildcard is unsafe, and `:112` sets it false — guarded by `tests/test_cors_config.py`. But your sessions are bearer tokens attached by client code, not cookies, so `allow_credentials=False` constrains nothing here. Narrow to an explicit origin list once the web client is in scope. Native clients send no `Origin` and are unaffected.

**v2.1 scope decision:** do not include CORS hardening in this authentication implementation.

### 2.13 — Cloud Run + Cloud SQL is the confirmed production architecture

**v2.1 decision:** current `main` uses Cloud Run as the backend deployment target and Cloud SQL/PostgreSQL as the production database architecture. Fly.io is retained only as rollback/history and must not be treated as an active deployment target for current `main`.

Mobile development, preview, production, and API fallback configuration now point to the Cloud Run service.

`APP_SESSION_SECRET` remains a runtime secret and therefore cannot be validated by repository inspection. During implementation, verify once that the active Cloud Run service has the expected session-secret configuration. This is a deployment verification checkpoint, **not an open architecture decision** and not a reason to redesign the auth system.

Do not add Fly.io compatibility work to this feature.


### 2.14 — Google Places key finding — separate secrets workstream

`AIzaSyBSPJNFu3Z3h-q7wiffZ2XzkSrXnpgLBu4` appears in all three `eas.json` profiles. Anything prefixed `EXPO_PUBLIC_` is inlined into the JS bundle at build time and extractable from any installed app — removing it from git changes nothing. **Restrict it instead:** bundle ID + SHA-1 fingerprint, Places APIs only, and check billing for scraper usage. The PostHog `phc_` key is fine; it is a public write-only ingest key.

Same principle applies to the Google OAuth client ID you're about to add. It is public by design; security comes from bundle-ID restriction plus backend signature/audience verification. Don't let anyone build a workaround treating it as a secret.

**v2.1 scope decision:** do not include Google Places key remediation in this authentication implementation. OAuth client validation remains in scope because it is directly part of authentication.

### 2.15 — Email deliverability has no fallback once passwords are gone

`api/services/email.py:18` sends from `Fueling2Win <onboarding@resend.dev>` — Resend's shared sandbox domain, under the old brand name. Your own §3 examples include `athlete@school.org`; district filters will quarantine sandbox mail, and with no password there is **zero** path into the app for that family.

Before launch: verified sending subdomain, SPF/DKIM/DMARC, bounce and complaint handling, and a support-side manual verification path.

**Also —** **`email.py:20`** **puts the OTP code in the email subject line.** Subject lines render on lock screens, in previews, and are logged by mail gateways. Move it into the body only.

### 2.16 — Data model gaps

- `auth_identities` needs a second constraint: one active row per `(provider, parent_id)`, or a user accumulates duplicate Google rows.
- One `parent_id` per identity leaves no room for **two parents sharing an athlete** — common in dual-guardian and divorced households. Add the join-table shape now even if you don't build it, so you aren't migrating live identity data later.
- §45's "normalized email matching": lowercase and trim only. Do **not** strip Gmail dots or `+suffixes` for account *linking* — aggressive normalization can collapse two distinct real accounts into one. Require the provider's `email_verified` flag before any auto-link (§16 says this loosely; make it a hard precondition).

## Part 3 — Structural edits: make the spec smaller

### 3.1 — Do not broaden this feature into a global token-framework refactor

The codebase contains similar HMAC token implementations in `session_auth.py`, `teamcoach_auth_service.py`, and `admin_auth.py`.

That duplication may be worth cleaning up later, but **v2.1 decision #5 applies here: this authentication feature must stay narrow**.

Therefore:

- Do **not** refactor TeamCoach or admin authentication merely to create a universal token framework.
- Keep the existing AthFuelPath session-token mechanism as the base for authenticated app sessions.
- If the verified-signup flow needs a temporary token, implement the smallest auth-local mechanism needed, with an explicit purpose/type and short expiry.
- The parent-generated athlete invitation is a short code, not a general session token. Store only what is required to bind it to the parent + athlete, expire it after 15 minutes, and mark it consumed after use.
- Do not introduce a general session `jti`/revocation framework in this P0 feature.

A broader token-library consolidation can be considered later as a separate engineering refactor.


### 3.2 — Collapse §25, §26, §27 into one funnel

The three methods differ in exactly one step: obtaining a verified `(provider, subject, email, email_verified)` tuple. Everything after is identical.

```
verify_google(id_token)       ─┐
verify_apple(id_token)        ─┼→ (provider, subject, email) → resolve_identity() → issue_session()
verify_email_otp(email, code) ─┘

```

Written as three separate 9-step lists, you will get three divergent implementations and three places to fix every future bug. Rewrite as "one resolver, three verifiers, here's the contract." §47's six negative tests then collapse into a parameterized loop.

### 3.3 — Testing: extend, don't create

`tests/test_auth_flow.py`, `test_session_auth.py`, and `test_confirmations_bola.py` already exist backend-side. Mobile `jest.config.js` already matches `__tests__/flows/**`, so §46 has a home. §45/§46/§47 list ~40 tests; only §47's negatives need hand-writing.

## Part 4 — Approved phased implementation order

The development agent must execute these phases sequentially. **Do not reinterpret or expand the scope beyond this v2.1 specification.**

### Phase 0 — Immediate containment

**0A. Stop athlete claim from calling `/api/auth/login`.**

- Remove the path that causes an unverified caller to receive a parent session token.
- Use only the minimum temporary behavior necessary until the invitation-code flow replaces claim lookup.
- No endpoint used here may return a parent session token to an unverified caller.

**0B. Add global 401 handling in `services/api.ts`.**

- A real `401` must clear the AthFuelPath session globally and route to authentication.
- Do not globally sign out on every `403`; a `403` may represent authorization failure rather than an invalid session.

> Authorization/BOLA cleanup outside these direct auth dependencies is a separate P0 workstream and is not part of v2.1.

### Phase 1 — Email authentication foundation

1. Migrate `otp_codes` from `parent_id`-keyed to normalized-email-keyed.
2. Add `attempts` and `consumed_at`.
3. Replace `random.randint` with a cryptographically secure generator (`secrets` or equivalent).
4. Remove OTP from the email subject line.
5. Keep the existing resend/expiry behavior, adding incorrect-attempt limits.
6. Prepare production email delivery under the AthFuelPath brand/domain.

### Phase 2 — Secure email authentication

1. Implement `/api/auth/email/request`.
2. Implement `/api/auth/email/verify`.
3. Use neutral, non-enumerating responses.
4. Successful verification resolves the identity and issues a real AthFuelPath session.
5. Email-only knowledge must never issue a session.

### Phase 3 — Session restoration

1. Implement `GET /api/auth/session` (or equivalent token-validation endpoint).
2. Update `authStore` / hydration so a valid stored AthFuelPath token is sufficient to restore the session.
3. Stored email must not be required for restoration.
4. Validate role + parent/athlete context from the token/server, not from locally trusted IDs.
5. This phase must be complete before old email-login call sites are removed.

### Phase 4 — Remove all email-only session issuance

Delete/replace every mobile/backend call path where an email alone can mint or refresh an AthFuelPath session, including the currently identified login, silent-restore, athlete-claim, and success/revalidation call sites.

After this phase:

> Knowing an AthFuelPath user's email address alone must be insufficient to obtain a session token anywhere in the system.

**Phases 0–4 close the critical email-only authentication vulnerability.**

### Phase 5 — Common identity resolver

Implement one shared authentication funnel:

```text
verify_google(...)       ─┐
verify_apple(...)        ─┼→ verified identity → resolve_identity() → issue_session()
verify_email_otp(...)    ─┘
```

The resolver owns account matching/linking rules. Provider-specific code only proves identity.

### Phase 6 — Google + Apple sign-in

Ship Google and Apple together against the common resolver.

Requirements include:

- server-side provider-token verification;
- issuer/audience/expiry verification;
- provider-supported nonce/state replay protection;
- explicit allowlist of valid AthFuelPath Google client audiences;
- Apple `usesAppleSignIn`/capability configuration;
- persist Apple first-authorization data needed for onboarding;
- support Apple Hide My Email;
- never authenticate from a client-supplied email field alone.

### Phase 7 — Verified signup/onboarding

1. Authentication occurs before account creation.
2. Issue a temporary verified-signup context/token.
3. `/api/onboarding/complete` must require that verified context.
4. Identity from the verified context, not an arbitrary request email, determines the account being created/linked.
5. Prevent duplicate account creation when the verified identity already resolves to an AthFuelPath account.

### Phase 8 — Parent-authorized athlete invitation code

Implement the approved v2.1 invitation-code flow from §2.6A.

No parent-email profile discovery may remain as the athlete authorization mechanism.

### Phase 9 — Existing-account migration / forced reauthentication

1. Existing beta users complete one secure reauthentication using Apple, Google, or verified email.
2. Link the verified identity to the existing AthFuelPath account.
3. Do not preserve insecure email-only compatibility just to avoid reauthentication.

### Phase 10 — Account deletion integration

Ensure in-app account deletion correctly handles linked authentication identities. If Sign in with Apple is linked, revoke the Apple authorization as part of deletion.

Do not use this phase to build general session revocation; that remains P1.

### Phase 11 — Launch verification

1. Run backend + mobile auth suites.
2. Run negative security tests.
3. Verify the legacy web login dependency is either migrated or intentionally retired before removing its required route.
4. Verify active Cloud Run runtime auth configuration, including `APP_SESSION_SECRET`.
5. Confirm no unverified endpoint returns a session token, even as an ignored/unused response field.
6. Only then consider enabling `PUBLIC_SIGNUP_ENABLED`.

## Final Scope Rule

**The development agent must execute v2.1 in the phases above and must not reinterpret or expand the scope beyond this specification.**

If a separate audit issue is discovered or encountered during implementation:

- record it;
- do not silently fix it inside this work unless it blocks a v2.1 phase;
- if it blocks a phase, make only the minimum dependency fix required;
- report it as a separate workstream rather than broadening this project.

The goal of v2.1 is a secure, modern AthFuelPath authentication system with:

- Apple sign-in;
- Google sign-in;
- verified-email fallback;
- token-based session restoration;
- verified signup;
- parent-authorized athlete invitation codes;
- no email-only session issuance.

Nothing more is implied.
